## Ejercicio 9.1 · Función genérica swapValues

> [!question] Enunciado
> Define una función parametrizada llamada `swapValues` que tenga un único parámetro de tipo `T`. La función debe aceptar dos parámetros mutables (`var`) llamados `firstElement` y `secondElement`, ambos de tipo `T`.
>
> Dentro del cuerpo de `swapValues`, implementa la lógica necesaria para intercambiar los valores de `firstElement` y `secondElement` (necesitarás una variable temporal). La función no debe devolver nada.
>
> En la función `main`:
>
> - Declara dos variables mutables (`var`) de tipo `String` llamadas `nameOne` y `nameTwo`, y asígnales valores iniciales diferentes.
> - Declara dos variables mutables (`var`) de tipo `Int` llamadas `numberOne` y `numberTwo`, y asígnales valores iniciales diferentes.
> - Llama a `swapValues` para intercambiar los valores de las variables de cadena (`nameOne`, `nameTwo`).
> - Llama a `swapValues` para intercambiar los valores de las variables enteras (`numberOne`, `numberTwo`).
> - Finalmente, imprime los valores de las cuatro variables, verificando que los intercambios se hayan realizado correctamente.

> [!warning] El enunciado no se puede hacer tal cual en Kotlin
> En Kotlin **los parámetros de una función son siempre `val`**: escribir `var firstElement: T` da el error de compilación `'var' on function parameter is prohibited` (comprobado con `kotlinc`). Además, aunque se pudieran reasignar, solo cambiaría la copia local del parámetro, no las variables de `main`: es lo mismo que pasa en Java, donde un método `swap(a, b)` tampoco intercambia las variables de quien lo llama.
>
> La solución mantiene lo importante del ejercicio (una función genérica con un único `T` que se usa con `String` y con `Int`, y una variable temporal), pero **devuelve** el resultado en un `Pair<T, T>` que `main` desestructura.

### Clases y métodos introducidos
- `fun <T> swapValues(...)`: el parámetro de tipo se declara entre `fun` y el nombre de la función.
- `Pair<T, T>`: agrupa dos valores del mismo tipo `T` (visto en [[07 - POO II#Pair y Triple|Pair y Triple]]).
- `val (a, b) = pair`: desestructuración del par en dos variables.

> **Términos explicados:** [[09 - Genéricos#2. Funciones parametrizadas|2. Funciones parametrizadas]]

### Código fuente (`Ejercicio9.1/src/Main.kt`)

```kotlin
// Versión literal del enunciado: NO compila.
// fun <T> swapValues(var firstElement: T, var secondElement: T) { ... }
// ↑ Error: en Kotlin los parámetros de una función son siempre val,
//   así que no se pueden declarar con var ni reasignar dentro de la función.

// Versión que funciona: la función genérica devuelve los dos valores ya intercambiados
fun <T> swapValues(firstElement: T, secondElement: T): Pair<T, T> {
    val temp = firstElement            // variable temporal, como pide el enunciado
    return Pair(secondElement, temp)
}

fun main() {
    var nameOne = "Ana"
    var nameTwo = "Luis"
    var numberOne = 1
    var numberTwo = 2

    // T se infiere como String y luego como Int
    val (newNameOne, newNameTwo) = swapValues(nameOne, nameTwo)
    nameOne = newNameOne
    nameTwo = newNameTwo

    val (newNumberOne, newNumberTwo) = swapValues(numberOne, numberTwo)
    numberOne = newNumberOne
    numberTwo = newNumberTwo

    println("nameOne = $nameOne, nameTwo = $nameTwo")
    println("numberOne = $numberOne, numberTwo = $numberTwo")
}
```

> [!tip] Salida por consola
> ```text
> nameOne = Luis, nameTwo = Ana
> numberOne = 2, numberTwo = 1
> ```

### Explicación paso a paso
1. Al principio se deja comentada la versión literal del enunciado y el error que produce.
2. `swapValues` es genérica: el mismo código vale para cualquier tipo `T`, y el compilador comprueba que los dos argumentos sean del mismo tipo.
3. Guarda el primer valor en `temp` y devuelve `Pair(secondElement, temp)`, es decir, los valores ya intercambiados.
4. En `main` no se escribe `swapValues<String>(…)`: el compilador **infiere** `T = String` a partir de los argumentos, y en la segunda llamada infiere `T = Int`.
5. El par se desestructura y se reasigna a las variables `var` originales, que es lo que hace que el intercambio se vea al imprimirlas.

## Ejercicio 9.2 · Clase genérica DataStore

> [!question] Enunciado
> Define una clase parametrizada llamada `DataStore` que acepte un único parámetro de tipo `T`. Dentro de la clase `DataStore`:
>
> - Declara una propiedad mutable (`var`) llamada `storedData` de tipo `T?` (para permitir que se inicialice o se vacíe).
> - Define una función llamada `saveData` que acepte un parámetro `newData` de tipo `T` y lo asigne a `storedData`.
> - Define una función `retrieveData` que devuelva el valor de `storedData` (de tipo `T?`).
>
> En la función `main`:
>
> - Crea una instancia inmutable de `DataStore` llamada `stringStore` y asígnale el valor inicial de `"Initial String"` al crear la instancia (permitiendo la inferencia de tipos).
> - Llama a `saveData` en `stringStore` con una nueva cadena de texto.
> - Crea una instancia inmutable de `DataStore` llamada `intStore` y asígnale el valor inicial `null` (deberás especificar el tipo genérico explícitamente, por ejemplo, `Int`).
> - Llama a `retrieveData` en ambas instancias e imprime sus resultados.

### Clases y métodos introducidos
- `class DataStore<T>`: clase con un parámetro de tipo que se usa en sus propiedades y métodos.
- `T?`: versión nullable del parámetro de tipo, para poder guardar `null`.
- Inferencia del argumento de tipo a partir del constructor (`DataStore("…")` → `DataStore<String>`).

> **Términos explicados:** [[09 - Genéricos#3. Clases e interfaces parametrizadas|3. Clases e interfaces parametrizadas]]

### Código fuente (`Ejercicio9.2/src/Main.kt`)

```kotlin
// T se decide al crear cada instancia
class DataStore<T>(private var storedData: T?) {

    fun saveData(newData: T) {
        storedData = newData
    }

    fun retrieveData(): T? = storedData
}

fun main() {
    // T se infiere como String a partir del argumento
    val stringStore = DataStore("Initial String")
    stringStore.saveData("Updated String")

    // Con null el compilador no puede inferir T: hay que indicarlo
    val intStore = DataStore<Int>(null)

    println("stringStore: ${stringStore.retrieveData()}")
    println("intStore: ${intStore.retrieveData()}")
}
```

> [!tip] Salida por consola
> ```text
> stringStore: Updated String
> intStore: null
> ```

### Explicación paso a paso
1. `storedData` se declara en el constructor primario como `private var` de tipo `T?`, para poder darle el valor inicial al crear la instancia.
2. `saveData` recibe un `T` (no nullable) y lo guarda; `retrieveData` devuelve un `T?`, porque puede no haber dato.
3. `DataStore("Initial String")` no lleva `<String>`: el compilador lo deduce del argumento.
4. `DataStore(null)` no compilaría, porque con `null` no hay forma de saber qué es `T`. Por eso se escribe `DataStore<Int>(null)`.

## Ejercicio 9.3 · Clase NullableWrapper con T?

> [!question] Enunciado
> Define una clase parametrizada llamada `NullableWrapper` que acepte un único parámetro de tipo `T`. Esta clase simulará un contenedor de valor que puede estar vacío. Dentro de la clase `NullableWrapper`:
>
> - Declara una propiedad inmutable (`val`) llamada `content` que debe ser de tipo `T?`. Inicializa esta propiedad directamente en el constructor primario de la clase.
> - Define una función `isEmpty` que devuelva un `Boolean`. Esta función debe comprobar si `content` es `null`.
> - Define una función `getOrDefault` que acepte un parámetro `defaultValue` de tipo `T` y devuelva un valor de tipo `T`. Esta función debe devolver `content` si no es `null`, y `defaultValue` en caso contrario.
>
> En la función `main`:
>
> - Crea una instancia inmutable de `NullableWrapper` llamada `wrapperOne`, especificando explícitamente que su tipo de contenido es `Int?` (es decir, `NullableWrapper<Int?>`). Inicialízala con el valor `10`.
> - Crea una segunda instancia inmutable `wrapperTwo`, especificando también que el tipo de contenido es `Int?`, pero inicialízala con el valor `null`.
> - Llama a `getOrDefault` en ambas instancias, pasando `0` como `defaultValue`.
> - Imprime el resultado de `getOrDefault` para ambas instancias y el resultado de `isEmpty` para `wrapperTwo`.

### Clases y métodos introducidos
- Un argumento de tipo puede ser nullable: `NullableWrapper<Int?>` hace que `T = Int?`.
- Operador Elvis `?:`: devuelve el valor de la izquierda si no es `null` y, si lo es, el de la derecha.

> **Términos explicados:** [[09 - Genéricos#4. Genéricos y tipos nullables|4. Genéricos y tipos nullables]]

### Código fuente (`Ejercicio9.3/src/Main.kt`)

```kotlin
class NullableWrapper<T>(val content: T?) {

    fun isEmpty(): Boolean = content == null

    // Elvis: si content es null, devuelve defaultValue
    fun getOrDefault(defaultValue: T): T = content ?: defaultValue
}

fun main() {
    val wrapperOne = NullableWrapper<Int?>(10)
    val wrapperTwo = NullableWrapper<Int?>(null)

    println("wrapperOne.getOrDefault(0) = ${wrapperOne.getOrDefault(0)}")
    println("wrapperTwo.getOrDefault(0) = ${wrapperTwo.getOrDefault(0)}")
    println("wrapperTwo.isEmpty() = ${wrapperTwo.isEmpty()}")
}
```

> [!tip] Salida por consola
> ```text
> wrapperOne.getOrDefault(0) = 10
> wrapperTwo.getOrDefault(0) = 0
> wrapperTwo.isEmpty() = true
> ```

### Explicación paso a paso
1. `content` es `val` de tipo `T?` y se declara directamente en el constructor primario.
2. `isEmpty()` es una función de expresión única que compara con `null`.
3. `getOrDefault` usa `content ?: defaultValue`: si hay contenido lo devuelve y, si no, devuelve el valor por defecto. El resultado es de tipo `T`.
4. Con `NullableWrapper<Int?>`, `T` es `Int?`, así que `T?` sigue siendo `Int?`: no pasa nada por poner `?` a un tipo que ya es nullable.
5. `wrapperOne` devuelve `10`; `wrapperTwo` está vacío, así que devuelve el `0` por defecto e `isEmpty()` es `true`.

## Ejercicio 9.4 · Jerarquía genérica Container y SimpleStorage

> [!question] Enunciado
> Define la siguiente jerarquía de interfaces y una clase, usando el parámetro de tipo `T`:
>
> - **Interface `Container<T>`:** Define un método llamado `fetch` que no acepte argumentos y devuelva un valor de tipo `T?`.
> - **Interface `MutableContainer<T>`:** Esta interfaz debe **heredar** de `Container<T>`. Además, define un método llamado `place` que acepte un parámetro `item` de tipo `T` y no devuelva nada.
> - **Clase `SimpleStorage<T>`:** Esta clase debe **implementar** la interfaz `MutableContainer<T>`.
>     - Debe tener una propiedad mutable (`var`) privada llamada `_item` de tipo `T?`.
>     - Implementa `fetch` para devolver el valor de `_item`.
>     - Implementa `place` para asignar `item` a `_item`.
>
> En la función `main`:
>
> - Crea una instancia inmutable de `SimpleStorage` para manejar valores de tipo `Int`.
> - Llama a `place` para guardar el número `42`.
> - Llama a `fetch` y guarda el resultado en una variable inmutable.
> - Imprime el resultado, verificando que la seguridad de tipos se mantiene en toda la jerarquía.

### Clases y métodos introducidos
- `interface MutableContainer<T> : Container<T>`: al heredar de una interfaz genérica hay que darle un argumento de tipo; aquí se le pasa el propio `T` de la interfaz hija.
- `_item`: el guion bajo es la convención para una propiedad privada "de respaldo".

> **Términos explicados:** [[09 - Genéricos#5. Parámetros de tipo y herencia|5. Parámetros de tipo y herencia]]

### Código fuente (`Ejercicio9.4/src/Main.kt`)

```kotlin
interface Container<T> {
    fun fetch(): T?
}

// El T de MutableContainer se pasa como argumento al T de Container
interface MutableContainer<T> : Container<T> {
    fun place(item: T)
}

class SimpleStorage<T> : MutableContainer<T> {
    private var _item: T? = null

    override fun fetch(): T? = _item

    override fun place(item: T) {
        _item = item
    }
}

fun main() {
    val storage = SimpleStorage<Int>()
    storage.place(42)
    // storage.place("42")   // Error de compilación: se esperaba Int
    val result: Int? = storage.fetch()
    println("Valor recuperado: $result")
}
```

> [!tip] Salida por consola
> ```text
> Valor recuperado: 42
> ```

### Explicación paso a paso
1. `Container<T>` solo sabe leer (`fetch`); `MutableContainer<T>` añade la escritura (`place`).
2. El `T` de cada interfaz es independiente: en `MutableContainer<T> : Container<T>` el `T` de la hija se usa como argumento del `T` del padre.
3. `SimpleStorage<T>` implementa los dos métodos sobre `_item`, que empieza en `null`.
4. Al crear `SimpleStorage<Int>()`, toda la jerarquía queda fijada a `Int`: `place("42")` daría error de compilación y `fetch()` devuelve `Int?`.

## Ejercicio 9.5 · Restricciones con Identifiable, Loggable y where

> [!question] Enunciado
> Define una función parametrizada `processInventoryItem` que acepte un único parámetro `item` de tipo `T`. Esta función debe imprimir un mensaje que indique que el ítem ha sido procesado. Restringe el parámetro de tipo `T` para que solo acepte tipos que implementen la interfaz `Identifiable`. Define una interfaz llamada `Identifiable` con una propiedad abstracta `id` de tipo `Int`.
>
> Define una segunda función parametrizada llamada `saveAndLog` que acepte un único parámetro `data` de tipo `T`. Esta función debe simular guardar y luego loguear los datos.
>
> Define una interfaz llamada `Loggable` con un método `logDetails` que no tome argumentos y no devuelva nada. Asegúrate de que `saveAndLog` use la cláusula `where` para exigir que `T` implemente **tanto** `Identifiable` **como** `Loggable`. Dentro de `saveAndLog`, llama a `data.logDetails()`.
>
> Crea una clase `Product` que implemente ambas interfaces. Crea una clase `Tool` que implemente solo `Identifiable`. Crea una clase `Report` que no implemente ninguna.
>
> En `main`, prueba la llamada a ambas funciones con las clases `Product`, `Tool` y `Report`, comentando qué llamadas fallan en tiempo de compilación debido a las restricciones.

### Clases y métodos introducidos
- `fun <T : Identifiable>`: restricción (_upper bound_). `T` debe ser `Identifiable` o un subtipo suyo.
- `where T : Identifiable, T : Loggable`: varias restricciones a la vez; `T` tiene que cumplirlas todas.
- Gracias a la restricción, dentro de la función se pueden usar `item.id` y `data.logDetails()`.

> **Términos explicados:** [[09 - Genéricos#7. Restricciones en los parámetros de tipo|7. Restricciones en los parámetros de tipo]]

### Código fuente (`Ejercicio9.5/src/Main.kt`)

```kotlin
interface Identifiable {
    val id: Int
}

interface Loggable {
    fun logDetails()
}

// T solo puede ser Identifiable o un subtipo suyo
fun <T : Identifiable> processInventoryItem(item: T) {
    println("Ítem ${item.id} procesado")   // podemos usar id gracias a la restricción
}

// Varias restricciones: T debe ser Identifiable Y Loggable
fun <T> saveAndLog(data: T) where T : Identifiable, T : Loggable {
    println("Guardando el ítem ${data.id}...")
    data.logDetails()
}

class Product(override val id: Int, private val name: String) : Identifiable, Loggable {
    override fun logDetails() {
        println("LOG -> Product(id=$id, name=$name)")
    }
}

class Tool(override val id: Int) : Identifiable

class Report(val title: String)

fun main() {
    val product = Product(1, "Teclado")
    val tool = Tool(2)
    val report = Report("Informe mensual")

    processInventoryItem(product)   // OK: Product es Identifiable
    processInventoryItem(tool)      // OK: Tool es Identifiable
    // processInventoryItem(report) // Error de compilación: Report no es Identifiable

    saveAndLog(product)             // OK: Product es Identifiable y Loggable
    // saveAndLog(tool)             // Error de compilación: Tool no es Loggable
    // saveAndLog(report)           // Error de compilación: Report no es ninguna de las dos
}
```

> [!tip] Salida por consola
> ```text
> Ítem 1 procesado
> Ítem 2 procesado
> Guardando el ítem 1...
> LOG -> Product(id=1, name=Teclado)
> ```

### Explicación paso a paso
1. `processInventoryItem` acepta `Product` y `Tool`, porque los dos son `Identifiable`.
2. `saveAndLog` solo acepta `Product`, la única clase que implementa las dos interfaces.
3. Las llamadas comentadas fallan **en compilación**, no en ejecución. Al descomentarlas, `kotlinc` dice, por ejemplo: `actual type is 'Tool', but 'Identifiable & Loggable' was expected`.
4. `Tool(override val id: Int) : Identifiable` no tiene cuerpo, porque la única propiedad abstracta ya se implementa en el constructor.

## Ejercicio 9.6 · Star projection en inspectContainer

> [!question] Enunciado
> Define una función llamada `inspectContainer` que acepte un parámetro inmutable `container` de tipo **`List<*>`**.
>
> Dentro de `inspectContainer`, la función debe realizar lo siguiente:
>
> - Imprimir el número de elementos en la lista (usando la propiedad `size`).
> - Intentar (y fallar, lo cual debe ser comentado) acceder directamente al primer elemento de la lista y llamarle a un método específico de `String` como `toUpperCase()`. **Esto debe fallar en tiempo de compilación**, demostrando que el compilador solo garantiza el tipo `Any?` al obtener datos.
> - Utiliza la función `forEach` o un bucle `for` para iterar sobre los elementos. Dentro del bucle, comprueba el tipo de cada elemento usando `is String` e imprime "Elemento String encontrado" si la condición es verdadera.
>
> En la función `main`:
>
> - Declara una lista inmutable `mixedList` que contenga una mezcla de tipos, por ejemplo, `"Hello"`, `42`, y `true`.
> - Llama a `inspectContainer` pasando `mixedList`.

### Clases y métodos introducidos
- `List<*>`: lista de "algo", sin importar de qué. Al leer, cada elemento es `Any?`.
- `is String` + _smart cast_: dentro del `if`, el compilador ya trata el elemento como `String`.
- `uppercase()`: la versión actual de `toUpperCase()`, que está obsoleta en Kotlin.

> **Términos explicados:** [[09 - Genéricos#8. Star projection|8. Star projection]]

### Código fuente (`Ejercicio9.6/src/Main.kt`)

```kotlin
fun inspectContainer(container: List<*>) {
    println("La lista tiene ${container.size} elementos")

    // container[0].uppercase()
    // ↑ Error de compilación: con List<*> cada elemento se obtiene como Any?,
    //   y Any? no tiene el método uppercase() (ni toUpperCase()) de String.

    for (element in container) {
        if (element is String) {
            // Smart cast: dentro del if, element ya es String
            println("Elemento String encontrado: ${element.uppercase()}")
        }
    }
}

fun main() {
    val mixedList = listOf("Hello", 42, true)
    inspectContainer(mixedList)
}
```

> [!tip] Salida por consola
> ```text
> La lista tiene 3 elementos
> Elemento String encontrado: HELLO
> ```

### Explicación paso a paso
1. `size` funciona con cualquier lista, sea del tipo que sea, así que con `List<*>` se puede usar sin problema.
2. `container[0].uppercase()` está comentado porque `container[0]` es `Any?`. Al descomentarlo, `kotlinc` da `unresolved reference 'uppercase'`.
3. En el `for`, `element is String` comprueba el tipo **en ejecución**. Se puede porque se pregunta por un tipo concreto (`String`), no por `T`.
4. Dentro del `if` hay _smart cast_, y por eso ahí sí se puede llamar a `uppercase()`.
5. `listOf("Hello", 42, true)` es una `List<Any>`, que se puede pasar donde se espera una `List<*>`.

## Ejercicio 9.7 · Varianza con DataProducer y DataConsumer

> [!question] Enunciado
> Define una clase `MediaFile` y una clase `VideoFile` que **herede** de `MediaFile`.
>
> Define dos interfaces genéricas:
>
> - **`DataProducer<T>`**: Define un único método `produceData` que no acepte argumentos y devuelva un objeto de tipo `T`. Define bien la varianza de `T`.
> - **`DataConsumer<T>`**: Define un único método `consumeData` que acepte un parámetro `data` de tipo `T` y no devuelva nada. Define bien la varianza de `T`.
>
> Crea dos clases concretas que implementen estas interfaces (puedes usar la sintaxis `object` para simplicidad):
>
> - `VideoProducer`: Implementa `DataProducer<VideoFile>`. El método `produceData` debe devolver una nueva instancia de `VideoFile`.
> - `MediaConsumer`: Implementa `DataConsumer<MediaFile>`. El método `consumeData` debe imprimir los detalles del `MediaFile` recibido.
>
> En la función `main`, utiliza las varianzas definidas para las siguientes asignaciones:
>
> | Tipo Deseado | Expresión Asignada | ¿Válido? | ¿Varianza Aplicada? |
> | --- | --- | --- | --- |
> | `DataProducer<MediaFile>` | `VideoProducer` | **Sí/No** | [Indica la varianza aplicada] |
> | `DataConsumer<VideoFile>` | `MediaConsumer` | **Sí/No** | [Indica la varianza aplicada] |
> | `DataProducer<VideoFile>` | `VideoProducer` | **Sí/No** | [Indica la varianza aplicada] |
>
> Escribe el código de las asignaciones e imprime un mensaje que indique el éxito o el fallo de cada una. Comenta por qué las asignaciones válidas son seguras.

### Clases y métodos introducidos
- `out T`: `T` solo aparece como tipo de **retorno** → covarianza (`DataProducer<VideoFile>` es subtipo de `DataProducer<MediaFile>`).
- `in T`: `T` solo aparece como tipo de **parámetro** → contravarianza (`DataConsumer<MediaFile>` es subtipo de `DataConsumer<VideoFile>`).
- `object VideoProducer : DataProducer<VideoFile>`: declaración de objeto (_singleton_) que implementa la interfaz.

> **Términos explicados:** [[09 - Genéricos#9. Varianza (invarianza, covarianza y contravarianza)|9. Varianza (invarianza, covarianza y contravarianza)]]

### Código fuente (`Ejercicio9.7/src/Main.kt`)

```kotlin
open class MediaFile(val name: String) {
    open fun details(): String = "MediaFile: $name"
}

class VideoFile(name: String, private val durationSeconds: Int) : MediaFile(name) {
    override fun details(): String = "VideoFile: $name (${durationSeconds}s)"
}

// out: T solo sale (productor) → covariante
interface DataProducer<out T> {
    fun produceData(): T
}

// in: T solo entra (consumidor) → contravariante
interface DataConsumer<in T> {
    fun consumeData(data: T)
}

object VideoProducer : DataProducer<VideoFile> {
    override fun produceData(): VideoFile = VideoFile("intro.mp4", 90)
}

object MediaConsumer : DataConsumer<MediaFile> {
    override fun consumeData(data: MediaFile) {
        println("Consumiendo -> ${data.details()}")
    }
}

fun main() {
    // 1. Covarianza: un productor de VideoFile sirve como productor de MediaFile,
    //    porque todo lo que produce (un VideoFile) ES un MediaFile.
    val mediaProducer: DataProducer<MediaFile> = VideoProducer
    println("1. DataProducer<MediaFile> = VideoProducer -> OK (covarianza)")

    // 2. Contravarianza: un consumidor de MediaFile sirve como consumidor de VideoFile,
    //    porque sabe tratar cualquier MediaFile, y un VideoFile lo es.
    val videoConsumer: DataConsumer<VideoFile> = MediaConsumer
    println("2. DataConsumer<VideoFile> = MediaConsumer -> OK (contravarianza)")

    // 3. Mismo tipo exacto: no hace falta ninguna varianza
    val videoProducer: DataProducer<VideoFile> = VideoProducer
    println("3. DataProducer<VideoFile> = VideoProducer -> OK (sin varianza, mismo tipo)")

    // Asignación NO válida (no compila):
    // val wrong: DataConsumer<MediaFile> = object : DataConsumer<VideoFile> { ... }
    // ↑ un consumidor de VideoFile no sabe tratar cualquier MediaFile

    // Uso de las variables
    MediaConsumer.consumeData(mediaProducer.produceData())
    videoConsumer.consumeData(videoProducer.produceData())
}
```

> [!tip] Salida por consola
> ```text
> 1. DataProducer<MediaFile> = VideoProducer -> OK (covarianza)
> 2. DataConsumer<VideoFile> = MediaConsumer -> OK (contravarianza)
> 3. DataProducer<VideoFile> = VideoProducer -> OK (sin varianza, mismo tipo)
> Consumiendo -> VideoFile: intro.mp4 (90s)
> Consumiendo -> VideoFile: intro.mp4 (90s)
> ```

### Explicación paso a paso
1. `produceData()` solo **devuelve** `T`, así que `DataProducer` se declara `out T`. `consumeData()` solo **recibe** `T`, así que `DataConsumer` se declara `in T`. Si los cambiaras de sitio, el compilador daría error.
2. **Asignación 1:** quien espera un productor de `MediaFile` recibirá siempre un `VideoFile`, que **es** un `MediaFile`. Es seguro (como la bolsa de manzanas cuando pedimos fruta).
3. **Asignación 2:** quien espera un consumidor de `VideoFile` solo le pasará vídeos, y `MediaConsumer` sabe tratar cualquier `MediaFile`. Es seguro (como la licuadora de fruta cuando pedimos una de manzanas).
4. **Asignación 3:** el tipo coincide exactamente, así que no interviene la varianza.
5. Lo contrario no compila. La asignación comentada (un consumidor de `VideoFile` usado como consumidor de `MediaFile`) da `initializer type mismatch`, porque podría recibir un `MediaFile` que no es un vídeo.

Tabla del enunciado resuelta:

| Tipo Deseado | Expresión Asignada | ¿Válido? | ¿Varianza Aplicada? |
| --- | --- | --- | --- |
| `DataProducer<MediaFile>` | `VideoProducer` | **Sí** | Covarianza (`out`) |
| `DataConsumer<VideoFile>` | `MediaConsumer` | **Sí** | Contravarianza (`in`) |
| `DataProducer<VideoFile>` | `VideoProducer` | **Sí** | Ninguna (mismo tipo) |
