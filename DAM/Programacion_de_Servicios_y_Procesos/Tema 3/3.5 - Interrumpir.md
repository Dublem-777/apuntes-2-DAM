## 1. Motivos para interrumpir un hilo

Como hemos visto, un programa Java con más de un hilo de ejecución continúa ejecutándose hasta que todos sus hilos (que no sean demonios) finalizan su ejecución, o hasta que uno de sus hilos invoca el método `System.exit()` para terminar la aplicación completa. Sin embargo, en muchas situaciones prácticas, es necesario poder finalizar la ejecución de un hilo concreto de forma controlada y bajo demanda, sin tener que esperar a que termine por sí solo de forma natural. Esta necesidad de finalización controlada de hilos puede surgir por diversas razones, como por ejemplo:

- **Cancelar una tarea en curso**: Si un hilo está ejecutando una tarea de larga duración (como un cálculo complejo, una operación de red, etc.) y el usuario o la aplicación decide cancelar esa tarea antes de que termine, necesitamos un mecanismo para indicar al hilo que debe detener su ejecución inmediatamente.
- **Finalizar un hilo al terminar su utilidad**: En algunas aplicaciones, un hilo puede ser necesario solo durante un cierto tiempo o para realizar una tarea específica, y una vez que esa tarea se ha completado o ya no es necesario, queremos finalizar el hilo para liberar recursos del sistema y evitar que siga consumiendo CPU innecesariamente.
- **Cerrar la aplicación de forma controlada**: En aplicaciones multihilo, antes de finalizar la aplicación completa, es conveniente asegurarse de que todos los hilos han terminado correctamente y han liberado los recursos que pudieran estar utilizando. Para ello, necesitamos un mecanismo para indicar a cada hilo que debe finalizar su ejecución de forma ordenada.

## 2. Mecanismo de interrupción

![Interrupción de un hilo](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/thread_interrupt.png)
*Interrupción de un hilo*

Para hacer frente a esta necesidad de finalización controlada de hilos, Java proporciona un mecanismo de interrupción que permite indicar a un hilo que se desea que finalice su ejecución. Este mecanismo de interrupción en Java tiene una característica importante y peculiar: no es un mecanismo de finalización forzosa e inmediata, sino que es un mecanismo cooperativo.

Esto significa que es el propio hilo el que debe comprobar periódicamente si ha sido interrumpido o no, y decidir si aceptar la solicitud de finalización y terminar su ejecución de forma ordenada, o ignorar la solicitud y seguir con su ejecución (aunque no es el comportamiento que se espera de un hilo bien programado en caso de interrupción). Si el hilo decide aceptar la interrupción y finalizar, simplemente retornará (hará `return`) del método `run()`, lo que provocará la terminación natural del hilo.

La clase `Thread` mantiene internamente un atributo booleano (un flag o bandera) que indica si el hilo ha sido interrumpido o no. Inicialmente, este atributo está a `false` para todos los hilos.

Cuando se llama al método `interrupt()` de un objeto `Thread` desde otro hilo, lo que ocurre es que se establece este atributo booleano a `true` para el hilo sobre el que se ha invocado `interrupt()`.

Es importante entender que el método `interrupt()` no fuerza la terminación inmediata del hilo. El método `interrupt()` simplemente envía una señal o solicitud de interrupción al hilo, activando su bandera de interrupción (poniéndola a `true`). Es responsabilidad del propio hilo (del código que se está ejecutando dentro del hilo) comprobar periódicamente el valor de esta bandera de interrupción y actuar en consecuencia, decidiendo si debe finalizar su ejecución de forma ordenada o continuar con su tarea (aunque lo esperado es que el hilo responda a la interrupción y termine de forma cooperativa).

> [!danger] Nunca hagas esto
> Nunca uses el método `stop()` de la clase Thread

La clase `Thread` dispone de un método llamado `stop()` que parece a primera vista que podría servir para forzar la finalización inmediata de un hilo. El método `stop()` efectivamente fuerza que un hilo deje de ejecutarse de forma abrupta e inmediata, sin darle tiempo a realizar ninguna operación de limpieza o liberación de recursos. Pero esta forma de actuar es extremadamente peligrosa e insegura. El método `stop()` es inherentemente inseguro y puede provocar graves problemas en la aplicación multihilo, como corrupción de datos, inconsistencia de estado, liberación incorrecta de recursos, bloqueos inesperados, y comportamiento impredecible e inestable de la aplicación.

## 3. Comprobación de haber sido interrumpido

> [!warning] Aviso
> `Thread.interrupted()` retorna el _flag_ de interrumpido y lo establece a `false`

Podemos utilizar el método de instancia `isInterrupted()` para consultar el valor actual de la bandera de interrupción de un hilo en particular. El método `isInterrupted()` retorna `true` si la bandera de interrupción del hilo está activada, y `false` en caso contrario. El método `isInterrupted()` no modifica el valor de la bandera de interrupción, simplemente lo consulta.

Por tanto, dentro del método `run()` del hilo deberemos comprobar periódicamente el valor de `isInterrupted()` para comprobar si se ha solicitado la interrupción del hilo.

**Consulta de si el hilo marcado para interrupción**
```java
public class MyRunnable implements Runnable {

    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            // ...
        }
    }

}
```

## 4. El método estático Thread.interrupted()

Existe otro método en la clase `Thread`, en este caso estático, llamado `Thread.interrupted()` que retorna si el hilo que se está ejecutando ha sido interrumpido o no, y establece dicho atributo a `false`.

Es fundamental tener cuidado con el método estático `Thread.interrupted()`, ya que su comportamiento es ligeramente diferente al del método de instancia `isInterrupted()` y puede llevar a errores sutiles si no se comprende bien su funcionamiento.

El método estático `Thread.interrupted()` realiza dos acciones atómicas en una sola llamada: primero, retorna el valor actual de la bandera de interrupción del hilo actual (el hilo que está ejecutando la llamada a `Thread.interrupted()`), y segundo, e inmediatamente después, establece la bandera de interrupción de ese mismo hilo a `false`.

Esta característica de borrar la bandera de interrupción después de consultarla hace que el método `Thread.interrupted()` sea menos adecuado para la comprobación periódica de la interrupción dentro de un bucle o de un método `run()`.

El método `Thread.interrupted()` es más adecuado para ser utilizado por el propio hilo, fuera del bucle de comprobación de interrupción, en situaciones muy específicas donde se quiere comprobar si el hilo ha sido interrumpido y al mismo tiempo limpiar la bandera de interrupción, para que no se propague más la señal de interrupción, siempre y cuando el hilo esté implementando una política de cancelación.

> [!tip] Consejo
> En general se prefiere usar `isInterrupted()` frente a `Thread.interrupted()`.

En la gran mayoría de los casos de programación multihilo en Java, y especialmente cuando se trabaja con `Runnable`, se prefiere utilizar el método de instancia `isInterrupted()` frente al método estático `Thread.interrupted()` para comprobar el estado de interrupción de un hilo, debido a su comportamiento más seguro, predecible y adecuado para la cooperación en la gestión de la interrupción.

## 5. Interrupción y métodos bloqueantes

Un aspecto muy importante del mecanismo de interrupción en Java es su interacción con las operaciones bloqueantes de los hilos. En la programación multihilo, es muy común que un hilo se vea bloqueado o en espera mientras realiza ciertas operaciones que pueden tardar un tiempo indeterminado en completarse, como por ejemplo las operaciones `wait()`, `join()`, `sleep()` (que veremos más adelante), o las llamadas de E/S bloqueantes, como operaciones de lectura o escritura en ficheros, sockets de red, pipes, terminales, etc.

Todas estas operaciones se denominan "operaciones bloqueantes" porque tienen la capacidad de poner al hilo en estado de bloqueo o espera, deteniendo su progreso hasta que se cumpla una determinada condición.

El mecanismo de interrupción en Java está especialmente diseñado para interactuar de forma cooperativa con estas operaciones bloqueantes. Si un hilo intenta ejecutar alguna de estas operaciones bloqueantes (como `wait()`, `join()`, `sleep()`, o llamadas de E/S bloqueantes), y en ese momento o mientras está bloqueado en la operación, dicho hilo tiene activado su bandera booleana de interrupción, la llamada al método bloqueante no se completará de forma normal, sino que lanzará automáticamente la excepción `InterruptedException`.

De forma similar, si un hilo ya está bloqueado en alguna de estas operaciones bloqueantes, y se le activa el valor booleano de interrupción desde otro hilo (se llama a `thread.interrupt()` desde otro hilo mientras el hilo está bloqueado), el hilo que estaba bloqueado será desbloqueado inmediatamente (saldrá del estado de bloqueo) y se le lanzará automáticamente la excepción `InterruptedException`.

La excepción `InterruptedException` es la forma en que Java señala a un hilo que ha sido interrumpido mientras estaba realizando una operación bloqueante. La excepción `InterruptedException` no es un error en sí mismo, sino que es parte del mecanismo de interrupción cooperativa. La excepción `InterruptedException` es la forma en que el hilo coopera con la solicitud de interrupción, indicando que ha recibido la señal de interrupción y que va a intentar finalizar su ejecución de forma ordenada.

Cuando un hilo recibe una excepción `InterruptedException`, debe capturar esta excepción en un bloque `catch` y gestionar la interrupción de forma adecuada, normalmente terminando la ejecución del método `run()` (haciendo `return`) para finalizar el hilo de forma controlada.

Piensa en `InterruptedException` como una señal muy específica. Si un método te _obliga_ a manejarla (es una _checked exception_), es porque es un **método de bloqueo** (como `sleep()`, `wait()`, `join()`, `take()` de un `BlockingQueue`, `lockInterruptibly()` de un `ReentrantLock`, etc.).

Cualquier método bien diseñado en la biblioteca estándar de Java (como los del paquete `java.util.concurrent`) que lanza `InterruptedException` cumple con el siguiente contrato: al capturar esta excepción se **limpia el estado de interrupción** en el _flag_ o indicador de interrupción, para que sea el código que captura la excpeción la que decida qué hacer. Este hecho puede causar problemas al código que se encuentre más arriba en la pila de llamadas (_call stack_) y que necesite saber sobre la interrupción.

Por eso, la práctica recomendada es volver a marcar el hilo como interrumpido en el bloque `catch`, llamando a `Thread.currentThread().interrupt()`, si queremos que el código superior (quien llamó a nuestro método) se entere de que la interrupción ocurrió.

**Excepción InterruptedException**
```java
public class MyRunnable implements Runnable {

    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            // ...
            try {
                Thread.sleep(sleepingTime);
            } catch (InterruptedException e) {
                // The thread has been interrupted
                Thread.currentThread().interrupt();
                return;
            }
        }
    }

}
```

Si lo que queremos es detener la ejecución inmediatamente en respuesta a la interrupción, otra opción es envolver (_wrap_) la `InterruptedException` en una `RuntimeException` y lanzarla, lo que permite que la interrupción se propague hacia arriba por la pila de llamadas, incluso a través de métodos que no declaran `InterruptedException` en su cláusula `throws`. Esto es particularmente útil en contextos donde no puedes añadir _checked exceptions_ a las firmas de los métodos (como al implementar interfaces que no las declaran).

Cuando el código de un hilo no es sencillo, como por ejemplo en el caso de que el código del `run()` llame a otros métodos, o que utilice recursividad, el método descrito anteriormente de capturar directamente la excepción `InterruptedException` dentro del bucle `run()` puede llegar a ser complejo de implementar y mantener. En estos casos más complejos, es mejor opción dejar que los métodos internos del hilo lancen la excepción `InterruptedException` cuando detecten que el hilo ha sido marcado como interrumpido, y propagar la excepción hacia arriba en la cadena de llamadas, hasta que finalmente la excepción llegue al método `run()`, donde la capturaremos en un bloque `catch` y gestionaremos la interrupción terminando el hilo. Para ello, los métodos internos que puedan realizar operaciones bloqueantes (o que llamen a otros métodos que puedan hacerlo) deben declarar que lanzan la excepción `InterruptedException` en su cláusula `throws InterruptedException` en la firma del método. Dentro de estos métodos, en lugar de capturar la excepción InterruptedException directamente, simplemente la dejamos propagar hacia el método llamador.

**Excepción InterruptedException en funciones recursivas**
```java
public class MyRunnable implements Runnable {

    @Override
    public void run() {
        try {
            recursiveMethod(initialValue);
        } catch (InterruptedException e) {
            // The thread has been interrupted
            return;
        }
    }

    private void recursiveMethod(int value) throws InterruptedException {
        // ...
    }

}
```

En general, debemos decidir qué hacer cuando detectamos que el hilo ha sido marcado para interrupción. Tenemos varias opciones:

- Propagar la excepción `InterruptedException` simplemente no capturándola.
- Capturar la excepción, realizar operaciones de liberaciones de recursos obtenidos por el hilo y después relanzar la excepción.
- Capturar la excepción y terminar.
- Capturar la excepción, restaurar el indicador de interrupción y terminar.

## 6. Proyecto Interrupt

En este proyecto vamos a desarrollar un programa sencillo que ilustra el mecanismo básico de interrupción cooperativa de hilos en Java, utilizando los métodos `interrupt()` e `isInterrupted()`. Crearemos un hilo dedicado a mostrar por pantalla números primos de forma indefinida, y desde el hilo principal, después de un cierto tiempo, solicitaremos al hilo impresor de números primos que finalice su ejecución utilizando el mecanismo de interrupción que hemos descrito anteriormente. Este proyecto nos permitirá ver en la práctica cómo se utiliza `interrupt()` para solicitar la interrupción de un hilo, y cómo el hilo debe comprobar periódicamente su estado de interrupción con `isInterrupted()` y responder a la interrupción terminando su ejecución de forma controlada.

**Proyecto Interrupt** · [▶ Replit](https://repl.it/@PedroJoya/PR004-Interrupt)

> [!warning] Código incompleto
> En Moodle el proyecto tiene las pestañas `Main`, `PrimeNumberPrinter`, pero al copiarlo solo se guardó **`Main`**.

`Main.java`
```java
public class Main {

    public static void main(String[] args) throws InterruptedException {
        Thread thread = new Thread(new PrimeNumberPrinter(), "Prime number printer");
        thread.start();
        // Sleep for 2 second.
        Thread.sleep(2000);
        // Active interruption flag in thread.
        thread.interrupt();
    }

}
```

Si ejecutamos el proyecto veremos que tan sólo se imprimen números durante dos segundos, dado que transcurrido dicho tiempo el hilo principal interrumpe el hilo secundario.

## 7. Proyecto InterruptedRecursiveFactorial

En este proyecto vamos a desarrollar un programa más elaborado que ilustra la técnica de propagación de la excepción `InterruptedException` para gestionar la interrupción de hilos en código más complejo, especialmente en funciones recursivas. Crearemos un hilo dedicado a mostrar por pantalla el factorial de los números naturales de forma indefinida, utilizando una función recursiva para calcular el factorial. Desde el hilo principal, después de un cierto tiempo, solicitaremos al hilo impresor de factoriales que finalice su ejecución utilizando el mecanismo de interrupción, y veremos cómo se propaga la excepción `InterruptedException` a través de las llamadas recursivas hasta llegar al método `run()`, donde se gestiona la interrupción y se termina el hilo de forma controlada. Este proyecto nos permitirá comprender mejor cómo manejar la interrupción en código recursivo y cómo utilizar la propagación de excepciones para simplificar la gestión de la interrupción en código complejo.

## Esquema

| Concepto | Sintaxis | Comportamiento |
|---|---|---|
| Pedir la interrupción | `hilo.interrupt()` | Pone el _flag_ a `true`; **no** para el hilo |
| Consultar | `Thread.currentThread().isInterrupted()` | No modifica el _flag_ (preferido) |
| Consultar y limpiar | `Thread.interrupted()` (estático) | Devuelve el _flag_ y lo pone a `false` |
| Métodos bloqueantes | `sleep()`, `join()`, `wait()`… | Lanzan `InterruptedException` y limpian el _flag_ |
| Restaurar el _flag_ | `Thread.currentThread().interrupt()` en el `catch` | Para que el código de arriba se entere |
| Código recursivo | `throws InterruptedException` hasta `run()` | Se captura una sola vez |
| Prohibido | `stop()` | Inseguro: corrompe datos y estado |
