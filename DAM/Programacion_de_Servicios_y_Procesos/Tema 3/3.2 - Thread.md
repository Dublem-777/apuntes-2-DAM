## 1. La clase Thread

![Thread](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/thread.png)
*Thread*

Java 1.0 fue lanzado en 1996 y venía con soporte incorporado (_built-in support_) para hilos (_threads_). Esta característica definitoria lo diferenció de muchos otros lenguajes de programación en aquel momento.

Esta API fundacional ha permanecido sin cambios durante casi tres décadas, demostrando la robustez de su diseño. Aunque Java ha añadido innumerables mejoras de concurrencia, desde `java.util.concurrent` hasta los hilos virtuales (_virtual threads_), estos bloques de construcción originales siguen siendo la base del modelo de hilos de Java.

En Java, la unidad fundamental de concurrencia, el hilo de ejecución, está representada por la clase `Thread`. La clase `Thread`, perteneciente al paquete `java.lang`, es la base sobre la que se construye toda la programación multihilo en Java. Si queremos crear y gestionar hilos en nuestros programas Java, necesitamos comprender y utilizar la clase `Thread` y sus métodos. Si queremos crear un hilo que ejecute un determinado código, deberemos definir una clase que extienda de la clase `Thread` y sobrescribir su método `run()`. Dicho método será ejecutado automáticamente por el sistema cuando iniciemos la ejecución del hilo.

Debemos tener en cuenta que si simplemente instanciamos la clase `Thread` usando su constructor vacío, `new Thread()`, estaremos creando un hilo que no ejecuta ningún código.

El método `run()` es el punto de entrada del código que se ejecutará en el nuevo hilo. Es en el método `run()` donde debemos implementar la lógica o las tareas que queremos que nuestro hilo realice de forma concurrente con el resto del programa. Cuando sobrescribimos el método `run()` en una clase que extiende de `Thread`, estamos definiendo el código que se ejecutará cuando se inicie el hilo.

> [!danger] Nunca hagas esto
> Nunca llames directamente al método `run()`. Debes llamar a `start()`

Sin embargo, llamar directamente al método `run()` no crea un nuevo hilo de ejecución. Si invocamos `miHilo.run()`, el código del método `run()` se ejecutará secuencialmente en el mismo hilo desde el que se realiza la llamada, como si fuera una llamada a un método normal, sin crear concurrencia.

El método `start()` es el método clave para iniciar la ejecución de un nuevo hilo. Cuando llamamos al método `start()` de un objeto Thread (por ejemplo, `miHilo.start()`), ocurren dos cosas importantes:

1. El método `start()` solicita al sistema operativo la creación de un nuevo hilo de ejecución para el objeto `Thread` sobre el que se invoca. El sistema operativo asigna los recursos necesarios para el nuevo hilo (como una pila de ejecución, un identificador de hilo, etc.) y lo registra en la tabla de hilos del sistema. La JVM también realiza la gestión interna necesaria para el nuevo hilo. Es en este momento, cuando se llama a `start()`, cuando se crea realmente el nuevo hilo de ejecución en el sistema operativo, no antes, cuando simplemente se instancia el objeto `Thread` con `new Thread()`.
2. Una vez que el hilo ha sido creado y registrado, el entorno de ejecución de Java llama internamente al método `run()` del objeto `Thread` en el nuevo hilo de ejecución que se ha creado. Esta llamada al método `run()` se realiza de forma asíncrona y concurrente con el hilo desde el que se llamó a `start()`. Esto significa que el hilo que llamó a `start()` continúa su ejecución inmediatamente después de invocar `start()`, sin esperar a que termine la ejecución del método `run()` en el nuevo hilo. El código del método `run()` se ejecutará concurrentemente con el resto del programa, en un hilo de ejecución separado.

**Extendiendo Thread**
```java
class MyThread extends Thread {

    @Override
    public void run() {
        // ...
    }

}
```

Para iniciar un objeto de dicha clase deberemos instanciarlo y llamar a su método `start()`:

**Iniciando un hilo**
```java
public class Main {

    public static void main(String[] args) {
        MyThread myThread = new MyThread();
        myThread.start();
    }

}
```

## 2. Restricciones en entornos visuales

![UI Thread](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/ui_worker_thread.png)
*UI Thread*

En general, dentro del método `run()` podemos ejecutar prácticamente cualquier código Java que queramos que se ejecute en el nuevo hilo. Sin embargo, en entornos visuales con interfaz de usuario (UI), como aplicaciones de escritorio con ventanas o aplicaciones móviles, pueden existir restricciones sobre qué hilos pueden acceder a los componentes de la interfaz de usuario. En muchos frameworks de UI (como Swing, JavaFX, Android UI, etc.), se impone la regla de que solo el hilo principal de la aplicación, el hilo de la interfaz de usuario (UI thread), puede acceder y modificar los componentes visuales de la interfaz gráfica.

En estos entornos, si un hilo secundario (un hilo trabajador) necesita actualizar la interfaz de usuario (por ejemplo, mostrar un resultado de un cálculo, actualizar una barra de progreso, etc.), no puede acceder directamente a los componentes de la UI y modificarlos. En su lugar, debe utilizar mecanismos de sincronización y comunicación específicos (como el paso de mensajes al hilo de la UI, o el uso de colas de eventos de la UI) para delegar la actualización de la interfaz al hilo de la UI, que es el único hilo autorizado para realizar estas operaciones de forma segura.

## 3. ¿Cuándo finaliza su ejecución un hilo?

Un hilo finaliza su ejecución automáticamente en cuanto se retorna de su método `run()`, ya sea por una salida anticipada mediante la instrucción return o simplemente porque se haya ejecutado la última instrucción del método `run()`. También puede terminar su ejecución abruptamente si el código del método `run()` lanza o produce una excepción que no es capturada dentro del método run(). En ambos casos, una vez que el hilo ha terminado su ejecución (ya sea de forma normal o por excepción), el hilo entra en el estado "Terminado" (_terminated_) y muere.

Una vez que un hilo ha finalizado su ejecución y ha entrado en el estado "Terminado", no puede volver a ejecutarse ni a ser reiniciado. Si intentamos llamar de nuevo al método start() de un objeto `Thread` que ya ha terminado su ejecución, se producirá una excepción de tipo `IllegalThreadStateException`.

> [!warning] Aviso
> Un hilo se finaliza cuando termina de ejecutarse su método `run()`

Por su parte, el planificador interno de hilos puede suspender y resumir la ejecución de un hilo muchas veces durante su ciclo de vida, algunas veces atendiendo a determinadas sentencias especificadas por el desarrollador dentro del código del hilo, y que estudiaremos más adelante, como `sleep()`, `wait()`, `notify()`, `join()`, etc.

Es importante tener en cuenta que, una vez que un hilo finaliza su ejecución (retorna de `run()`), el entorno de ejecución de Java (JVM) recicla los recursos del sistema operativo que fueron obtenidos para ese hilo, como por ejemplo, la memoria reservada para su pila de ejecución, el identificador de hilo, etc. Esto significa que no podemos reutilizar el mismo objeto `Thread` que corresponde a un hilo ya finalizado para ejecutar alguna otra tarea o para iniciar un nuevo hilo de ejecución. Un objeto `Thread` representa una única ejecución de un hilo (operación _one-shot_, de un solo disparo). Si queremos ejecutar una tarea concurrente otra vez o una tarea diferente, debemos crear un nuevo objeto `Thread` y volver a iniciarlo con `start()`.

## 4. ¿Cuándo finaliza un proceso con varios hilos?

Cuando un proceso posee múltiples hilos de ejecución, es importante entender cuándo termina la ejecución del proceso en su conjunto.

Un proceso continúa ejecutándose mientras al menos uno de sus hilos esté todavía en ejecución (es decir, no haya terminado su método `run()` y no haya entrado en el estado "Terminado").

Esto significa que, incluso si el hilo principal, es decir, el hilo que ejecuta el método `main()`, termina su ejecución, el proceso no finalizará inmediatamente si otros hilos (hilos secundarios) siguen en ejecución. El proceso seguirá ejecutándose hasta que todos los hilos que no sean hilos demonio (o hilos de servicio, que veremos más adelante) hayan terminado su ejecución.

Si, en cambio, uno de los hilos (sea el hilo principal o un hilo secundario) utiliza la instrucción `System.exit(código_de_salida)` para terminar la ejecución del programa Java, se finalizará inmediatamente la ejecución de todos los hilos del proceso, incluyendo el hilo que llamó a `System.exit()` y todos los demás hilos que pudieran estar todavía en ejecución. La instrucción `System.exit()` provoca una terminación abrupta e inmediata de todo el programa Java y de todos sus hilos, independientemente de su estado o de si han terminado o no su tarea.

## 5. Atributos de la clase Thread

La clase `Thread` proporciona una serie de atributos de información que nos pueden ser útiles para identificar un hilo, conocer su estado actual, o gestionar su prioridad. Estos atributos son:

- **ID**: Cada hilo tiene asignado un identificador numérico único dentro de la JVM. El ID de un hilo es un valor de tipo `long` que se genera automáticamente cuando se crea el hilo y que lo identifica de forma unívoca dentro de la JVM. En versiones recientes de Java (a partir de Java 19), el método `getId()` ha sido marcado como obsoleto y se recomienda usar en su lugar el nuevo método `threadId()` (`long idDelHilo = miHilo.threadId()`).
- **Name**: Cada hilo tiene asociado un nombre, que es una cadena de texto que sirve para identificar el hilo de forma más descriptiva y legible para los programadores (especialmente en tareas de depuración y monitorización). Si no se especifica un nombre al crear un hilo, la JVM le asigna automáticamente un nombre por defecto con el formato Thread-XX, donde XX es un número secuencial. Podemos obtener el nombre de un hilo utilizando el método `getName()`. Podemos asignar un nombre específico a un hilo de dos formas:

    - Pasando el nombre como argumento al constructor de la clase `Thread`: `Thread miHilo = new Thread(miRunnable, "Hilo-Procesador-De-Pedidos")`.
    - Utilizando el método `setName(String nombre)` del objeto `Thread`: `miHilo.setName("Hilo-Calculador-De-Estadisticas")`
- **Priority**: Cada hilo tiene asignada una prioridad, que es un valor entero que indica la importancia relativa del hilo con respecto a otros hilos a la hora de ser planificado por el scheduler de la JVM. La prioridad de un hilo es un valor entero entre 1 y 10, donde 1 representa la mínima prioridad y 10 representa la máxima prioridad. La prioridad por defecto de un hilo (si no se especifica otra) es 5 (prioridad normal). El método `setPriority()` puede lanzar una excepción `IllegalArgumentException` si se intenta establecer una prioridad que no esté entre `1` y `10`.

- **Status**: El estado de un hilo indica la fase actual de su ciclo de vida (ver apartado anterior sobre "Estados de un hilo"). El estado de un hilo puede ser uno de los siguientes valores de la enumeración `Thread.State`: `NEW` (nuevo), `RUNNABLE` (ejecutable o listo), `RUNNING` (corriendo o en ejecución), `BLOCKED` (bloqueado), `WAITING` (esperando), `TIMED_WAITING` (esperando por tiempo), o `TERMINATED` (terminado). El estado de un hilo es actualizado automáticamente por la JVM a medida que el hilo avanza en su ciclo de vida y cambia de estado. No es posible modificar el estado de un hilo directamente desde código. El programador solo puede observar el estado actual de un hilo utilizando el método `getState()` para monitorizar o depurar la aplicación multihilo.

> [!warning] Aviso
> La prioridad de los hilos es un mecanismo orientativo para el scheduler de la JVM, pero no garantiza un comportamiento determinista en la planificación de los hilos. El scheduler de la JVM intentará favorecer la ejecución de los hilos con mayor prioridad frente a los de menor prioridad, pero no es una garantía absoluta de que un hilo de mayor prioridad siempre se ejecute antes o durante más tiempo que un hilo de menor prioridad.

La planificación de hilos depende de muchos factores, como el sistema operativo subyacente, la carga del sistema, la implementación específica de la JVM, y el algoritmo de planificación utilizado por el scheduler. Por lo tanto, no se debe depender exclusivamente de la prioridad de los hilos para garantizar la sincronización o el orden de ejecución en programas multihilo.

La prioridad de los hilos es más útil para dar pistas al scheduler sobre la importancia relativa de los hilos, pero no para controlar de forma precisa la planificación.

## 6. Los hilos, las excepciones y el depurador

En Java, cada hilo (_thread_) tiene su propia pila de llamadas (_call stack_) separada, que registra todas las invocaciones de métodos realizadas durante el tiempo de vida del hilo. Cuando se lanza una excepción, la pila de llamadas de ese hilo se convierte en una parte vital del historial de diagnóstico; muestra la secuencia de invocaciones de métodos que condujeron a la excepción, ayudando a los desarrolladores a rastrear la causa raíz de un problema.

Esta traza (_trace_) permite a los desarrolladores inspeccionar la pila de llamadas dentro de un contexto de hilo (_thread_) específico (es decir, el contexto del hilo donde ocurrió la excepción). Esta granularidad es muy beneficiosa en la JVM, especialmente para depurar aplicaciones multihilo donde varios hilos pueden ejecutarse concurrentemente en las mismas o diferentes tareas. Este detalle nos ayuda a localizar problemas más rápido, haciendo que la depuración sea más enfocada y eficiente, y conduciendo a una resolución más rápida.

Al "engancharse" (_attaching_) a los diversos hilos de la aplicación, el depurador (_debugger_) puede seleccionar cuál de estos hilos individuales examinar, o incluso cambiar su estado mientras depura una aplicación activa. Esto es fundamental para la capacidad de encontrar y corregir errores (_bugs_) en aplicaciones donde varios hilos pueden estar ejecutándose simultáneamente en diferentes etapas, y donde diferentes hilos pueden estar interactuando de maneras que necesitan ser comprendidas.

Cada acción puede ser ejecutada "paso a paso por dentro" (_step into_), "paso a paso por encima" (_step over_), o "paso a paso saliendo de" (_step out_) con respecto a un hilo. Se pueden inspeccionar una o más pilas de llamadas independientes de los hilos activos en una sesión de depuración. La pila de llamadas nos dice qué sucedió antes, como qué causó que un hilo estuviera en un punto determinado de un programa. Comprender cómo un hilo llegó a cierto estado es inestimable cuando estamos tratando de averiguar la causa de una excepción inesperada o una manipulación de datos errónea.

## 7. Proyecto Thread

Para ilustrar de forma práctica cómo crear y utilizar hilos en Java extendiendo la clase `Thread` y sobrescribiendo el método `run()`, vamos a desarrollar un sencillo proyecto que muestra la tabla de multiplicar de los números del 1 al 10, utilizando un hilo de ejecución diferente para cada tabla de multiplicar. Este proyecto, aunque simple, nos permitirá ver en funcionamiento la creación y ejecución de múltiples hilos en Java y observar el comportamiento concurrente de los hilos en un programa multihilo. Para representar la tabla de multiplicar de un número, definiremos una clase llamada `MultiplicationTable` que extienda de la clase `Thread`.

**Proyecto Thread** · [▶ Replit](https://repl.it/@PedroJoya/PR001-Thread)

> [!warning] Código incompleto
> En Moodle el proyecto tiene las pestañas `Main`, `MultiplicationTable`, pero al copiarlo solo se guardó **`Main`**.

`Main.java`
```java
public class Main {

    public static void main(String[] args) {

        for (int i = 1; i <= 10; i++) {
            MultiplicationTable table = new MultiplicationTable(i);
            table.start();
            // ¡IMPORTANTE! start() NO bloquea la ejecución del hilo principal,
            // que continúa con la siguiente iteración del bucle.
            // Los hilos creados se ejecutarán de forma concurrente
            // con el hilo principal y entre sí.
        }
        // El hilo principal termina, pero el programa Java NO termina aquí,
        // ya que los 10 hilos MultiplicationTable siguen ejecutándose.
        // El programa Java continuará ejecutándose hasta que todos los hilos
        // terminen su ejecución.
    }

}
```

Al ejecutar el proyecto, podemos comprobar el comportamiento concurrente de los hilos. Observamos que el orden en que se muestran las líneas de las diferentes tablas de multiplicar no es secuencial y no coincide con el orden de creación de los hilos. Las líneas de salida de las diferentes tablas de multiplicar se entremezclan entre sí, y el orden exacto de las líneas puede variar en cada ejecución diferente del programa. Esto se debe a que los 10 hilos MultiplicationTable se están ejecutando de forma concurrente (en paralelo o por tiempo compartido), y el scheduler del sistema operativo (y de la JVM) es el que decide en qué orden y durante cuánto tiempo se ejecuta cada hilo en cada momento, y este orden no es determinista y puede variar entre ejecuciones.

Este comportamiento no determinista en el orden de ejecución de los hilos es una característica fundamental de la programación multihilo y de la concurrencia en general. En programas multihilo, no podemos predecir ni controlar el orden exacto en que se ejecutarán los hilos, sino que debemos diseñar nuestros programas para que funcionen correctamente independientemente del orden de ejecución de los hilos y para gestionar adecuadamente la concurrencia y la sincronización entre los hilos cuando sea necesario.

## 8. ¿Cuántos hilos podemos crear?

Un detalle importante a tener en cuenta es la huella de memoria (_memory footprint_) de cada hilo: unos 2 MB de memoria (aparte del _heap_ del que haga uso cada hilo). Esto puede convertirse rápidamente en mucho, especialmente en aplicaciones a gran escala que manejan miles de conexiones concurrentes, bajo un modelo de "hilo por petición" (_thread-per-request_), donde se asigna un hilo a cada petición.

Los hilos de Java son, en realidad, un envoltorio ligero (_thin wrapper_) alrededor de los hilos nativos proporcionados por el sistema operativo anfitrión. Esto significa que el número máximo de hilos que podemos crear para cualquier aplicación está, en la práctica, limitado por el límite de creación de hilos nativos que impone el sistema operativo anfitrión. Casi todos los sistemas operativos tienen un límite máximo en la cantidad de hilos que se pueden crear (_spawn_). Por lo tanto, el potencial de escalabilidad de una aplicación está limitado por este cuello de botella.

Además, debemos tener en cuenta el coste del cambio de contexto (_context switching_). La creación de hilos no es solo una sobrecarga (_overhead_) de memoria. Es también una sobrecarga de CPU. Cuando se cambia entre hilos, eso es un cambio de contexto. El contexto del hilo actual debe ser guardado, y el contexto del nuevo hilo debe ser restaurado. Todo ese cambio de contexto cuesta ciclos de CPU y, en sistemas bajo alta carga, esta sobrecarga puede suponer una diferencia enorme en el rendimiento. Esta es otra fuente de carga (_weight_) en una aplicación que a menudo se subestima.

Pero, entonces, ¿cuántos hilos podemos crear? Ejecutando un programa de prueba simple, podemos determinar el número máximo de hilos (_threads_) que nuestro sistema puede manejar antes de experimentar problemas.

**Número máximo de hilos**
```java
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.LockSupport;

public class ThreadLimitTest {
    public static void main(String[] args) {
        // Más adelante estudiaremos qué es un AtomicInteger.
        var threadCount = new AtomicInteger(0);
        try {
            while (true) {
                var thread = new Thread(() -> {
                    threadCount.incrementAndGet();
                    // Suspender el hilo de forma indefinida para evitar que termine.
                    // No usar en producción, solo para testing
                    LockSupport.park();
                });
                thread.start();
            }
        } catch (OutOfMemoryError error) {
            System.out.println("Reached thread limit: " + threadCount);
            error.printStackTrace();
        }
    }
}
```

Ejecútalo en tu sistema y prueba a ver cuál es tu límite de hilos. El programa lanzará una excepción `OutOfMemoryError` cuando se alcance se alcance el límite de memoria debido a la memoria necesaria para crear cada hilo.

## Esquema

| Concepto | Sintaxis | Comportamiento |
|---|---|---|
| Definir un hilo | `class X extends Thread` + `@Override run()` | `run()` es el código del hilo |
| Iniciar | `hilo.start()` | Crea el hilo en el SO y llama a `run()` en él |
| Llamar a `run()` | `hilo.run()` | ❌ Se ejecuta en el hilo actual, sin concurrencia |
| Reiniciar | `start()` dos veces | `IllegalThreadStateException` (un `Thread` es _one-shot_) |
| Fin del hilo | sale de `run()` (o excepción no capturada) | Pasa a `TERMINATED` |
| Fin del proceso | todos los hilos no daemon terminan · `System.exit()` | `exit` mata todos los hilos |
| Atributos | `threadId()`, `getName()`/`setName()`, `setPriority()`, `getState()` | Prioridad 1–10, por defecto 5 |
| Coste | ~2 MB por hilo + cambios de contexto | El SO limita el nº de hilos |
