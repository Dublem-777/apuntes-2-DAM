## 1. Proceso

En el mundo actual de la informática, la concurrencia se ha convertido en un concepto fundamental en el desarrollo de software. Cuando hablamos de concurrencia en ordenadores, nos referimos a la capacidad de un sistema para ejecutar múltiples tareas o partes de un programa aparentemente al mismo tiempo. Esta simultaneidad puede ser real, si el ordenador tiene más de un procesador o un procesador con varios núcleos (donde las tareas se ejecutan en paralelo en diferentes núcleos), o simulada, si el ordenador sólo dispone de un único núcleo de procesamiento (donde el sistema operativo alterna rápidamente entre las tareas, dando la ilusión de simultaneidad). Todos los sistemas operativos modernos permiten la ejecución de tareas concurrentes.

> [!definition] Proceso
> Unidad de reserva de memoria y de protección del sistema operativo

Un proceso es, desde la perspectiva del sistema operativo, la unidad básica de asignación de recursos del sistema, como memoria, ficheros abiertos, y otros recursos del sistema. También es una unidad de protección, ya que los procesos suelen tener espacios de memoria aislados entre sí, lo que impide que un proceso interfiera directamente con la memoria de otro proceso (protección de memoria).

Cuando iniciamos un programa, el sistema operativo crea un nuevo proceso para ejecutar ese programa. Cada proceso tiene su propio espacio de direcciones de memoria, y el sistema operativo gestiona y planifica la ejecución de los procesos, repartiendo el tiempo de la CPU entre ellos para lograr la multitarea a nivel de proceso.

## 2. ¿Qué es un hilo?

> [!definition] Hilo
> Unidad de ejecución de conjunto de instrucciones

Dentro de un proceso, podemos tener múltiples hilos de ejecución (o hebras), también conocidos como **threads** en inglés. Un hilo es la unidad básica de ejecución dentro de un proceso.

Podemos definir un hilo como una **secuencia de instrucciones que se ejecuta de forma concurrente con otros hilos dentro del mismo proceso**.

A diferencia de los procesos, **los hilos comparten el mismo espacio de memoria y los recursos del proceso al que pertenecen**, lo que facilita la comunicación y el intercambio de datos entre ellos, pero también requiere mecanismos de sincronización para evitar problemas de concurrencia (como condiciones de carrera o corrupción de datos).

Un proceso siempre tiene al menos un hilo, que es el hilo principal o hilo inicial. Este hilo principal puede, a su vez, crear nuevos hilos para realizar tareas en paralelo.

## 3. Hilo vs. Proceso

Aunque procesos e hilos permiten lograr concurrencia en un sistema informático, existen diferencias fundamentales entre ellos que debemos comprender para decidir cuándo es más apropiado utilizar procesos o hilos en el diseño de nuestras aplicaciones concurrentes.

Los hilos no pueden ejecutarse por sí solos, necesitan estar contenidos en un proceso padre. Cuando se crea un proceso (cuando se lanza la ejecución de un programa), se crea dentro de él un hilo principal, que puede, a su vez, crear tantos hilos como desee, que pasarán a ejecutarse contenidos dentro del proceso.

Los hilos del mismo proceso comparten el espacio de memoria del éste, incluyendo datos, código y recursos, mientras que los procesos generalmente disponen de espacios de memoria independientes.

La memoria necesaria para un hilo es menor que la necesaria para un proceso, porque un hilo comparte gran parte de los recursos del proceso padre. Por ejemplo, los siguientes elementos son compartidos por todos los hilos del proceso:

- Espacio de Direcciones de Memoria:
    - Código
    - Datos globales
    - _heap_.
- Recursos del Sistema Operativo: Descriptores de archivos, señales, etc.

Sin embargo, cada hilo dispone de su propio **TCB (_Thread Control Block_, bloque de control de hilo)**. La TCB es una estructura de datos fundamental utilizada por el sistema operativo para gestionar y mantener toda la información esencial de un **hilo de ejecución** (o _thread_). Es el equivalente del PCB (_Process Control Block_) para los hilos, pero contiene la información específica del hilo, mientras que el proceso al que pertenece el hilo tiene su propia PCB para la información compartida.

La TCB contiene la información privada del hilo, la cual es crucial para su ejecución y para que el sistema operativo pueda realizar tareas como la planificación y el cambio de contexto. Los campos almacenados en la TCB típicamente incluyen:

- **TID (_Thread Identification_):** Un identificador único para el hilo.
- **Contador de programa (_program counter_ o PC):** La dirección de la próxima instrucción a ejecutar, esencial para reanudar la ejecución.
- **Registros de la CPU:** Los valores de los registros del procesador que el hilo estaba utilizando antes de ser interrumpido. Esta información es vital para el **cambio de contexto**.
- **Pila (_stack_):** El puntero o una referencia a la pila de ejecución del hilo, utilizada para llamadas a funciones locales y variables.
- **Estado del hilo (_status_):** El estado actual del hilo (ej. listo, en ejecución, bloqueado).
- **Información de planificación:** Prioridad del hilo, punteros para listas de planificación.
- **Puntero al PCB:** Una referencia al **Bloque de Control de Proceso (PCB)** al que pertenece el hilo, ya que los hilos comparten recursos del proceso padre (como el espacio de direcciones de memoria).
- Almacenamiento local del hilo (TLS, _Thread-Local Storage_)

![TCP de hilo y memoria del proceso](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/threads_vs_process.jpg)
*TCP de hilo y memoria del proceso*

La TCB cumple dos funciones principales:

- **Gestión y seguimiento:** Permite al núcleo del sistema operativo rastrear el estado y la identidad de cada hilo en el sistema.
- **Cambio de contexto:** Cuando el sistema operativo decide interrumpir un hilo para ejecutar otro (un **cambio de contexto**), la TCB se utiliza para guardar el estado actual del hilo que se va a suspender (PC, registros de CPU) en su TCB, y cargar el estado guardado del próximo hilo a ejecutar desde su TCB a los registros de la CPU, permitiendo que el nuevo hilo continúe su ejecución exactamente desde donde se detuvo.

Dado que los hilos dentro del mismo proceso comparten el espacio de memoria, el cambio de contexto entre hilos es significativamente **más rápido** (menos costoso) que el cambio de contexto entre procesos, ya que no es necesario vaciar y recargar la caché y el TLB (_Translation Lookaside Buffer_, caché de traducción de direcciones virtuales a dirección físicas) como ocurre con el cambio de contexto entre procesos (donde se cambia todo el espacio de direcciones).

Los hilos del mismo proceso interactúan normalmente a través de mecanismos de sincronización establecidos por el desarrollador, mientras que los procesos interactuán entre sí a través de mecanismos de sincronización dados por el propio sistema.

## 4. ¿Para qué se usan los hilos?

Los hilos son usados normalmente para, dentro de un proceso, llevar a cabo distintas tareas simultáneamente, o para realizar tareas costosas en tiempo sin detener el resto del programa.

Por ejemplo en un proceso correspondiente a un editor de textos, podemos tener un hilo encargado de estar llevando a cabo la comprobación ortográfica del texto, o guardando automáticamente en documento en segundo plano cada cierto tiempo. Otro ejemplo típico es el de un servidor web que cada vez que recibe una petición crea uno nuevo para atenderla, permitiendo seguir recibiendo peticiones en el hilo principal.

Otro caso de uso habitual es cuando una aplicación debe descargar varios archivos de internet simultáneamente. Podríamos crear un hilo diferente para cada descarga de archivo. De esta manera, si una descarga se ralentiza (por ejemplo, debido a una conexión de red lenta o a un servidor remoto con baja capacidad de respuesta), sólo se bloqueará el hilo encargado de esa descarga específica, pero los otros hilos de descarga podrán seguir funcionando y descargando otros archivos en paralelo, sin que la aplicación se quede "colgada" o deje de responder. Una vez que todos los hilos de descarga hayan terminado, el hilo principal podría notificar al usuario que todas las descargas se han completado.

En los entornos gráficos (como aplicaciones de escritorio con ventanas, aplicaciones móviles, etc.), el hilo principal de una aplicación corresponde normalmente a lo que se conoce como hilo de la interfaz de usuario (UI thread o hilo de eventos). La misión principal del hilo de la interfaz de usuario es gestionar y actualizar la interfaz gráfica de la aplicación (ventanas, botones, textos, imágenes, etc.) y responder a los eventos e interacciones del usuario (clics de ratón, pulsaciones de teclado, gestos táctiles, etc.).

En estos sistemas, es críticamente importante que el hilo de la interfaz de usuario nunca quede bloqueado por una operación costosa o de larga duración. Si el hilo de la UI se bloquea (por ejemplo, mientras realiza un cálculo complejo, accede a un fichero grande en disco, o espera una respuesta de red), la aplicación dejará de responder a las interacciones del usuario, la interfaz gráfica se congelará o se colgará, y el usuario tendrá la sensación de que la aplicación no funciona correctamente o se ha bloqueado.

Por este motivo, en los entornos gráficos, todas las tareas que no sean prácticamente inmediatas (operaciones de red, acceso a disco, cálculos complejos, etc.) deben llevarse a cabo en hilos secundarios o hilos trabajadores (worker threads), de manera que estos hilos puedan realizar su trabajo en segundo plano y, si se bloquean, no afecten a la capacidad de respuesta y fluidez del hilo de la interfaz de usuario. El hilo de la UI se mantendrá siempre libre y disponible para atender las interacciones del usuario y mantener la interfaz gráfica actualizada y responsiva.

## 5. Ventajas e inconvenientes del uso de hilos

La utilización de hilos en la programación concurrente ofrece una serie de importantes beneficios que pueden mejorar significativamente el rendimiento, la capacidad de respuesta y la eficiencia de nuestras aplicaciones. Los principales beneficios de utilizar hilos son:

- Mejoran el rendimiento de la aplicación en hardware con varios núcleos de procesamiento, ya que se ejecutan en paralelo.
- Incrementan el rendimiento de la aplicación, ya que una llamada de E/S solamente bloqueará el hilo en el que se realiza.
- Aumentan la capacidad de respuesta de la aplicación, ya que un hilo de la UI puede estar atendiendo siempre las peticiones de usuario mientras otros hilos realizan otras tareas más costosas. El resultado es que el usuario no adquiere la sensación de que el programa esté "colgado".
- La comunicación entre hilos se puede realizar mediante variables, ya que todos los hilos del proceso comparten la memoria y los recursos asignados a éste. Sin embargo, este tipo de comunicación hace necesario el establecimiento de métodos de sincronización entre los hilos. En otros casos se lleva a cabo la comunicación entre hilos a través de paso de mensajes, como en el caso de entornos en el que el hilo principal está dedicado a la interfaz de usuario, como en el caso de Android.
- La creación de nuevos hilos necesitan una pila específica para cada uno de ellos.

Los hilos son una herramienta poderosa y fundamental para lograr concurrencia y mejorar el rendimiento y la capacidad de respuesta de las aplicaciones. Son especialmente útiles en situaciones donde:

- Se necesita realizar tareas que pueden ejecutarse en paralelo, aprovechando sistemas con múltiples núcleos de procesamiento.
- Se deben realizar operaciones que pueden ser bloqueantes (como operaciones de E/S, espera de respuestas de red, etc.), sin bloquear la ejecución del resto del programa, especialmente el hilo de la interfaz de usuario en aplicaciones gráficas.
- Se busca mejorar la capacidad de respuesta de la interfaz de usuario, manteniéndola siempre fluida y reactiva a las interacciones del usuario, incluso mientras se realizan tareas costosas en segundo plano.
- Se requiere compartir datos y recursos de forma eficiente entre diferentes partes de un programa, ya que los hilos comparten el espacio de memoria del proceso.

Sin embargo, la programación multihilo también introduce complejidades adicionales que debemos tener en cuenta. La principal complejidad surge de la necesidad de gestionar la concurrencia y la sincronización entre los hilos, para evitar problemas como las condiciones de carrera, los interbloqueos y la inanición.

Además, los programas multihilo pueden ser más difíciles de depurar y probar que los programas secuenciales, debido a la naturaleza no determinista de la ejecución concurrente y a la posibilidad de que los problemas de concurrencia sólo se manifiesten de forma intermitente o en ciertas condiciones de carga.

## 6. Los hilos y el sistema operativo

Para entender completamente cómo funcionan los hilos en nuestros programas Java, es importante conocer cómo los sistemas operativos modernos gestionan internamente los hilos y los procesos.

En sistemas operativos que soportan multithreading (multihilo), como Linux y Windows, el sistema operativo mantiene una tabla de procesos que contiene información no sólo sobre los procesos en ejecución, sino también sobre los hilos que pertenecen a cada proceso. Sin embargo, la forma en que se gestiona esta información y se representan los hilos en la tabla de procesos varía ligeramente dependiendo del sistema operativo. A continuación, veremos las diferencias principales en la gestión de hilos entre Linux y Windows.

En Linux, la gestión de hilos se realiza de una forma particular. En lugar de tener una estructura de datos separada para los hilos dentro de un proceso, Linux implementa los hilos como procesos ligeros (_lightweight processes_ o LWPs). Esto significa que cada hilo en Linux se representa en la tabla de procesos del sistema operativo con su propia entrada individual y su propio PID (Process ID), al igual que un proceso "normal". De ahí que se les conozca como procesos ligeros, ya que comparten muchos de los recursos del proceso padre, pero a nivel de sistema operativo se gestionan de forma similar a procesos independientes.

Sin embargo, para indicar que varios de estos "procesos ligeros" pertenecen al mismo proceso, los hilos de un mismo proceso comparten el mismo TGID (Thread Group ID), que corresponde al PID del proceso "padre" al que pertenecen. De esta forma, el sistema operativo Linux puede gestionar y planificar los hilos individualmente (ya que cada uno tiene su propio PID), pero también puede agruparlos y reconocer que pertenecen al mismo proceso (a través del TGID). Esta implementación de hilos como procesos ligeros en Linux tiene algunas implicaciones en cuanto a la gestión de recursos y la planificación, pero en general proporciona un modelo eficiente y flexible para la programación multihilo.

En Windows, la gestión de hilos se realiza de una forma diferente a Linux, con estructuras de datos específicas para representar procesos e hilos. El sistema operativo Windows utiliza dos estructuras de datos principales para gestionar procesos e hilos:

- EPROCESS (Executive Process Block): Es una estructura de datos del kernel de Windows que contiene información a nivel de proceso. Cada proceso en Windows tiene asociado una estructura EPROCESS que contiene información como el PID del proceso, el espacio de direcciones de memoria asignado al proceso, la lista de hilos que pertenecen al proceso, los recursos del sistema que tiene asignados, información de seguridad, etc. La estructura EPROCESS representa al proceso como una entidad contenedora de recursos y de hilos de ejecución.
- ETHREAD (Executive Thread Block): Es otra estructura de datos del kernel de Windows que contiene información a nivel de hilo. Cada hilo de ejecución en Windows tiene asociado una estructura ETHREAD que contiene información como el TID (Thread ID) del hilo, el estado actual del hilo (ejecutándose, listo, bloqueado, etc.), el contador de programa del hilo, la pila del hilo, y un puntero al EPROCESS del proceso al que pertenece el hilo. La estructura ETHREAD representa al hilo como una unidad de ejecución dentro de un proceso.

En Windows, la tabla de procesos (o más correctamente, las estructuras de datos internas del kernel que gestionan procesos e hilos) contiene información tanto a nivel de proceso (a través de las estructuras EPROCESS) como a nivel de hilo (a través de las estructuras ETHREAD). Cada hilo tiene su propio TID (Thread ID), que es un identificador único para cada hilo dentro del sistema Windows. Además, cada ETHREAD está vinculado al EPROCESS del proceso al que pertenece a través del PID de este proceso, estableciendo así la relación jerárquica entre procesos e hilos en Windows.

Este modelo de gestión de hilos en Windows permite al sistema operativo realizar un seguimiento detallado de cada hilo de ejecución y de su proceso padre, y gestionar la planificación y la asignación de recursos de forma eficiente.

Un punto fundamental a destacar es que, en sistemas operativos modernos que soportan multihilo (_multithreading_), **la asignación del núcleo de procesamiento (CPU core) por parte del scheduler (planificador) del sistema operativo se realiza a nivel de hilos, no de procesos**. Esta es una de las ventajas clave del multithreading y una de las razones por las que se utiliza ampliamente en programación concurrente. En lugar de planificar la ejecución de procesos completos, el sistema operativo planifica la ejecución de los hilos individuales dentro de un proceso (o de diferentes procesos). Esto significa que el scheduler del sistema operativo decide qué hilo de entre todos los hilos listos para ejecutarse (de todos los procesos del sistema) se ejecutará a continuación en un núcleo de la CPU, y durante cuánto tiempo. **La unidad de planificación es el hilo, no el proceso**.

De hecho, en sistemas con procesadores multinúcleo (multicore processors), el scheduler del sistema operativo puede ir más allá y asignar diferentes hilos de un mismo proceso a distintos núcleos de procesamiento de la CPU al mismo tiempo. Esto es lo que permite que varios hilos de un mismo proceso se ejecuten verdaderamente en paralelo, en núcleos de CPU separados, aprovechando al máximo la capacidad de procesamiento multinúcleo (multicore parallelism). Los hilos del proceso podrían estar ejecutándose simultáneamente en paralelo en sus respectivos núcleos, realizando trabajo de forma concurrente y reduciendo el tiempo total de ejecución de la aplicación.

Esta capacidad de paralelismo real a nivel de hilos es una de las principales razones por las que se utiliza el multithreading para desarrollar aplicaciones de alto rendimiento que pueden aprovechar al máximo las arquitecturas de hardware modernas con múltiples núcleos de procesamiento.

En sistemas con un único núcleo de procesamiento, la concurrencia de hilos sigue siendo útil para mejorar la capacidad de respuesta y gestionar operaciones bloqueantes, pero el paralelismo es simulado (por tiempo compartido), no real, ya que en un instante de tiempo dado, sólo un hilo puede estar ejecutándose en el único núcleo disponible.

## 7. Estados de un hilo

Para poder gestionar y controlar correctamente los hilos en nuestros programas Java, es fundamental comprender los diferentes estados por los que puede pasar un hilo a lo largo de su ciclo de vida, desde su creación hasta su finalización. Un hilo no está siempre en el mismo estado: puede estar ejecutándose, esperando a que ocurra algo, listo para ejecutarse, o finalizado. Entender estos estados y las transiciones entre ellos es esencial para escribir programas multihilo correctos, eficientes y sin problemas de concurrencia. A lo largo de su ejecución, un hilo puede pasar por los siguientes estados:

![Diagrama de estados de un hilo](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/thread_states.png)

### 7.1 Nuevo / Naciendo (new)

El estado **Nuevo / Naciendo (new)** es el estado inicial de un hilo, justo después de su creación. Cuando creamos un nuevo hilo en Java utilizando la palabra clave new (por ejemplo, `Thread miHilo = new Thread(miRunnable);`), se crea el objeto `Thread` correspondiente en memoria, y el hilo entra en el estado "Nuevo" o "Naciendo".

En este estado, el hilo existe, pero aún no está activo y no ha comenzado su ejecución. Todavía no se han asignado recursos del sistema operativo al hilo (más allá de la memoria para el objeto `Thread` en sí), y el hilo no es elegible para ser planificado por el _scheduler_ del sistema operativo.

En este estado, solo podemos realizar operaciones muy básicas sobre el hilo, como configurar su nombre o prioridad, pero no podemos iniciarlo todavía. Para que un hilo "Nuevo" comience a ejecutarse y pase al siguiente estado, debemos iniciarlo explícitamente invocando al método `start()` del objeto `Thread`.

### 7.2 Listo / Ejecutable (runnable)

Una vez que un hilo "Nuevo" ha sido iniciado mediante la llamada al método start(), el hilo pasa al estado **Listo / Ejecutable** (_runnable_). En este estado, el hilo ya está preparado para ser ejecutado y está compitiendo por tiempo de CPU con otros hilos listos del sistema. El hilo "Listo" ha sido admitido por el _scheduler_ del sistema operativo y se encuentra en la cola de hilos listos (o cola de preparados). Esto significa que el hilo está esperando a que el planificador del sistema operativo le asigne un núcleo de procesamiento (CPU core) para poder comenzar a ejecutar sus instrucciones.

Es importante destacar que estar en estado "Listo" no significa que el hilo se esté ejecutando realmente en ese instante. Significa que está preparado y a la espera de que el _scheduler_ le dé su turno de ejecución. El _scheduler_ es el encargado de decidir cuándo y durante cuánto tiempo cada hilo "Listo" pasa al estado "Corriendo" (running).

La transición del estado "Listo" al estado "Corriendo" es gestionada completamente por el sistema operativo y su planificador, y es transparente para el programador Java.

### 7.3 Corriendo / En ejecución (running)

Cuando el _scheduler_ del sistema operativo decide asignar tiempo de CPU a un hilo "Listo", el hilo pasa al estado **Corriendo / En ejecución** (_running_). En este estado, el hilo está realmente ejecutando sus instrucciones en un núcleo de procesamiento de la CPU. El hilo "Corriendo" tiene asignado un núcleo de CPU y está progresando en la ejecución de su método `run()` (o el código que se haya definido para el hilo). Durante el tiempo que el hilo permanece en estado "Corriendo", está activamente utilizando la CPU para realizar su tarea.

Un hilo puede permanecer en estado "Corriendo" durante un cierto tiempo (_quantum_) que le asigna el _scheduler_. Después de este tiempo, o si ocurre algún evento que provoque que el hilo deba esperar (por ejemplo, una operación de E/S, espera por un monitor, etc.), el hilo puede volver al estado "Listo" para que el _scheduler_ pueda asignar el núcleo de CPU a otro hilo, o puede pasar a otro estado como "Bloqueado" o "Suspendido".

La transición del estado "Corriendo" de vuelta al estado "Listo" o a otros estados también es gestionada por el sistema operativo y su planificador.

### 7.4 Bloqueado (blocked)

Un hilo entra en el estado **Bloqueado** (_blocked_) cuando intenta acceder a un recurso compartido (como un objeto, una variable, una sección de código, etc.) que está protegido por un objeto monitor (o cerrojo o mutex) y que en ese momento no está libre, sino que está siendo utilizado por otro hilo.

En Java, los objetos monitor se utilizan para implementar mecanismos de sincronización y exclusión mutua para proteger el acceso concurrente a recursos compartidos y evitar condiciones de carrera.

Cuando un hilo intenta entrar en una sección de código o acceder a un recurso que está protegido por un monitor que ya está adquirido (bloqueado) por otro hilo, el primer hilo se bloquea y entra en el estado "Bloqueado".

El hilo "Bloqueado" queda en espera de que el hilo que actualmente posee el monitor lo libere (lo desbloquee) para poder intentar adquirirlo y continuar su ejecución. Un hilo permanece en estado "Bloqueado" hasta que el monitor que estaba intentando adquirir se libera por parte del hilo que lo poseía.

Una vez que el monitor se libera, el hilo (o uno de los hilos en espera) puede intentar adquirirlo de nuevo y, si lo consigue, pasará al estado "Listo" (y eventualmente a "Corriendo") para continuar su ejecución en la sección crítica protegida por el monitor.

El estado "Bloqueado" es un mecanismo fundamental para implementar la sincronización y la exclusión mutua en programación multihilo, garantizando que el acceso a recursos compartidos se realice de forma controlada y segura.

### 7.5 Suspendido (waiting)

Un hilo entra en el estado **Suspendido / En Espera** (_waiting_) cuando voluntariamente decide suspender su propia ejecución y esperar a que ocurra un determinado evento o condición para poder continuar. A diferencia del estado "Bloqueado" (que es una suspensión involuntaria debido a la contención por un monitor), el estado "Suspendido" es una suspensión activa y controlada por el propio hilo a través de código. Un hilo puede entrar en estado "Suspendido" de varias formas, por ejemplo:

- Llamando al método `wait()` de un objeto monitor: Cuando un hilo invoca el método wait() de un objeto, libera el monitor de ese objeto (si lo poseía) y se suspende, entrando en la cola de espera de ese monitor. El hilo permanecerá en estado "Suspendido" hasta que otro hilo invoque el método `notify()` o `notifyAll()` del mismo objeto monitor, lo que le notificará que puede volver a intentar ejecutarse. Este mecanismo se utiliza para la sincronización basada en condiciones (_condition synchronization_).
- Llamando al método `join()` de otro hilo: Cuando un hilo A invoca el método `join()` de otro hilo B (por ejemplo, `hiloB.join()`), el hilo A se suspende y entra en estado "Suspendido" hasta que el hilo B termine su ejecución y muera. Este mecanismo se utiliza para esperar a que otro hilo complete su tarea antes de continuar.
- Llamando a métodos de pausa y espera de bajo nivel como `LockSupport.park()` (que suspende el hilo hasta que sea "desaparcado" con `LockSupport.unpark()`).

Un hilo en estado "Suspendido" no consume tiempo de CPU y no es elegible para ser planificado por el scheduler (a menos que se trate de "Suspendido por tiempo", ver siguiente estado).

Permanece en este estado hasta que reciba una notificación (por ejemplo, a través de `notify()`, `notifyAll()`, `unpark()`, o la finalización del hilo al que se hizo `join()`) que le indique que puede volver a intentar ejecutarse. Una vez notificado, el hilo vuelve al estado "Listo", para que el scheduler pueda volver a planificar su ejecución.

### 7.6 Suspendido por tiempo (timed waiting)

El estado **Suspendido por tiempo** (_timed waiting_) es una variante del estado "Suspendido" (waiting). Un hilo entra en estado "Suspendido por tiempo" cuando se suspende voluntariamente su ejecución, pero con un límite de tiempo máximo de espera. Es decir, el hilo se suspende y espera a que ocurra un determinado evento o a que transcurra un tiempo máximo especificado. Si ocurre el evento antes de que expire el tiempo, el hilo puede reanudar su ejecución antes. Si el tiempo expira antes de que ocurra el evento, el hilo se despertará automáticamente y volverá a estar listo para ejecutarse, incluso si el evento esperado no ha ocurrido. Ejemplos de acciones que llevan a un hilo al estado "Suspendido por tiempo" son:

- Llamando al método `Thread.sleep(tiempo)`: Este método suspende la ejecución del hilo actual durante un tiempo mínimo especificado en milisegundos. Una vez transcurrido ese tiempo (o más, dependiendo de la precisión del scheduler), el hilo se despierta automáticamente y vuelve al estado "Listo".
- Llamando a las versiones con timeout de los métodos `wait(timeout)`, `join(timeout)` y `parkNanos(nanos)`, `parkUntil(deadline)`: Estos métodos permiten suspender un hilo en espera de una notificación o de la finalización de otro hilo, pero estableciendo un tiempo máximo de espera. Si la notificación o la finalización del otro hilo no ocurre antes de que expire el timeout, el hilo se despertará automáticamente y volverá al estado "Listo", incluso si la condición de espera no se ha cumplido.

Un hilo en estado "Suspendido por tiempo" tampoco consume tiempo de CPU mientras está suspendido, y no es elegible para ser planificado hasta que se cumpla el tiempo de espera o reciba una notificación (si aplica). La diferencia con el estado "Suspendido" (waiting) es que en "Suspendido por tiempo" la suspensión tiene una duración máxima, mientras que en "Suspendido" (waiting) la suspensión puede ser indefinida hasta que se reciba una notificación. Una vez que el tiempo de espera expira o se recibe una notificación, el hilo vuelve al estado "Listo", para que el scheduler pueda volver a planificar su ejecución.

### 7.7 Terminado (terminated)

Este es el estado final de un hilo. Un hilo entra en el estado **Terminado** (terminated) o "Muerto" cuando ha finalizado su ejecución. Esto puede ocurrir de dos formas principales:

- **Finalización natural**: El hilo termina su ejecución de forma normal cuando el código de su método `run()` (o el `Runnable` o `Callable` asociado al hilo) llega al final y retorna (finaliza la ejecución del método `run()` de forma exitosa).
- **Finalización abrupta por excepción**: El hilo termina su ejecución de forma anormal si se produce una excepción no capturada dentro del método `run()` del hilo, y esta excepción se propaga hasta el nivel superior del hilo, provocando que el hilo termine abruptamente debido a la excepción.

Una vez que un hilo ha entrado en el estado "Terminado", no puede volver a ejecutarse ni a cambiar de estado. Es un estado final. El hilo ha muerto y ya no está activo.

El entorno de ejecución de Java (JVM) puede liberar los recursos del sistema operativo que estaban asociados al hilo terminado, como por ejemplo, la memoria de su pila, y la entrada del hilo en la tabla de hilos del sistema operativo puede ser eliminada (dependiendo de la implementación del sistema operativo y de la JVM).

Si intentamos realizar operaciones sobre un hilo que ya ha terminado (por ejemplo, intentar reiniciarlo o volver a ejecutar su método `run()`), se producirá una excepción de tipo `IllegalThreadStateException`, indicando que la operación no es válida en un hilo terminado.

## 8. Comunicación entre hilos

Una vez que hemos creado múltiples hilos dentro de un proceso para lograr concurrencia, surge la necesidad de que estos hilos puedan comunicarse y coordinarse entre sí para llevar a cabo tareas complejas de forma conjunta. La comunicación entre hilos es un aspecto fundamental de la programación multihilo, ya que permite que los hilos compartan información, sincronicen sus acciones y colaboren para lograr un objetivo común. Existen dos mecanismos principales para la comunicación entre hilos dentro de un mismo proceso:

### 8.1 A través de objetos compartidos en memoria

![Objetos compartidos](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/shared_object.png)
*Objetos compartidos*

Una de las formas más directas y eficientes de comunicación entre hilos que pertenecen a un mismo proceso es a través de la memoria compartida. Dado que todos los hilos de un proceso comparten el mismo espacio de memoria del proceso padre, pueden utilizar esta memoria común para intercambiar información y datos entre sí.

En este modelo de comunicación, los hilos se comunican indirectamente a través de objetos que residen en la memoria compartida del proceso. Un hilo puede escribir datos en un objeto compartido, y otros hilos del mismo proceso pueden leer esos mismos datos desde el mismo objeto compartido.

Este mecanismo de comunicación es muy rápido y eficiente, ya que no implica la intervención del sistema operativo para el intercambio de datos (como sí ocurre en la comunicación entre procesos).

Sin embargo, la comunicación mediante objetos compartidos también introduce desafíos importantes relacionados con la concurrencia y la sincronización, ya que múltiples hilos pueden acceder y modificar los mismos objetos compartidos al mismo tiempo, lo que puede dar lugar a problemas de corrupción de datos, condiciones de carrera y otros errores de concurrencia si no se gestiona adecuadamente.

Debido a que múltiples hilos pueden acceder y modificar simultáneamente los mismos objetos compartidos en memoria, es absolutamente esencial establecer mecanismos de sincronización de acceso a datos. Si no se implementa una sincronización adecuada, se pueden producir graves problemas de concurrencia.

Por lo tanto, la comunicación a través de objetos compartidos en memoria requiere siempre la utilización de mecanismos de sincronización (como monitores, cerrojos, semáforos, variables de condición, etc.) para controlar y coordinar el acceso concurrente a los objetos compartidos, garantizando la integridad de los datos y el correcto funcionamiento de la aplicación multihilo.

La comunicación entre hilos a través de objetos compartidos en memoria presenta tanto ventajas como desventajas que debemos considerar al elegir este mecanismo de comunicación en nuestros programas multihilo.

Entre las ventajas destacamos su alta eficiencia y rendimiento, su implicidad conceptual y su flexiblidad. Sin embargo también presenta una serie de desventajas, como la complejidad de la sincronización, el riesgo de errores de concurrencia y el menor aislamiento entre hilos.

En general, la comunicación por objetos compartidos es una técnica poderosa y eficiente, pero requiere mayor cuidado y experiencia en programación concurrente para evitar los riesgos asociados a la sincronización y la concurrencia.

En los casos donde la seguridad, la robustez y la facilidad de programación son prioritarias, el paso de mensajes puede ser una alternativa más adecuada, como veremos en el siguiente apartado.

### 8.2 A través de paso de mensajes entre hilos

![Paso de mensajes](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/message_passing.png)
*Paso de mensajes*

Una alternativa a la comunicación mediante objetos compartidos en memoria es el paso de mensajes entre hilos. En este modelo de comunicación, los hilos se comunican enviándose mensajes mutuamente, en lugar de acceder directamente a una memoria compartida.

Cada hilo posee una cola de mensajes (también llamada _message queue_ en inglés), que actúa como un canal de comunicación para recibir mensajes de otros hilos. Un hilo que quiere enviar información a otro hilo, construye un mensaje (que puede contener datos, comandos, notificaciones, etc.) y lo envía a la cola de mensajes del hilo destinatario. El sistema de paso de mensajes se encarga de entregar el mensaje a la cola buzón del hilo destino. La operación de envío de mensajes suele ser _asíncrona_, lo que significa que el hilo emisor no espera a que el mensaje sea procesado por el hilo receptor, sino que continúa con su ejecución inmediatamente después de enviar el mensaje.

El hilo receptor, en algún momento de su ejecución, consulta su cola de mensajes para ver si hay mensajes pendientes de ser procesados. Una vez que el hilo receptor ha extraído un mensaje de su cola, procesa el mensaje, extrae la información contenida en él, y realiza las acciones correspondientes en función del tipo de mensaje y de su contenido.

A diferencia de la memoria compartida, en el paso de mensajes los hilos no acceden directamente a la memoria del otro, sino que la comunicación es indirecta y asíncrona, a través del envío y recepción de mensajes. El sistema de paso de mensajes se encarga de la entrega de los mensajes desde el hilo emisor a la cola de mensajes del hilo receptor, proporcionando un mecanismo de comunicación desacoplado y asíncrono entre los hilos.

El paso de mensajes es un modelo de comunicación especialmente adecuado y ampliamente utilizado en los sistemas en los que el hilo principal de una aplicación corresponde al hilo de la interfaz de usuario (_UI thread_), y donde se impone la restricción de que solo el hilo de la interfaz de usuario puede actualizar la interfaz gráfica. Este es el caso, por ejemplo, de los sistemas operativos móviles como Android y iOS, y de muchos frameworks de desarrollo de interfaces gráficas de usuario en general.

![Paso de mensajes al hilo de UI en Android](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/looper_android.png)
*Paso de mensajes al hilo de UI en Android*

En estos sistemas, se utiliza el paso de mensajes como el mecanismo principal de comunicación entre los hilos trabajadores (que realizan tareas en segundo plano) y el hilo de la interfaz de usuario (que gestiona la interfaz gráfica y responde a los eventos del usuario). Cuando un hilo trabajador necesita notificar al hilo de la interfaz de usuario de que ha completado una tarea, de que se ha producido un evento, o de que hay datos que deben ser mostrados o actualizados en la interfaz gráfica, no puede acceder directamente a los objetos de la interfaz de usuario y modificarlos, ya que esto solo puede hacerlo el hilo de la UI.

En su lugar, el hilo trabajador envía un mensaje a la cola de mensajes del hilo de la interfaz de usuario, indicando la acción a realizar o los datos a actualizar. El hilo de la interfaz de usuario, en su bucle de eventos principal, procesa continuamente los mensajes que llegan a su cola de mensajes. Cuando recibe un mensaje de un hilo trabajador, el hilo de la UI extrae el mensaje de la cola, interpreta el mensaje, y realiza las actualizaciones necesarias en la interfaz gráfica (por ejemplo, actualizando un texto, mostrando una imagen, animando un elemento, etc.) de forma segura y sincronizada, ya que todo el acceso y la modificación de la interfaz gráfica se realiza siempre desde el propio hilo de la interfaz de usuario.

Este modelo de paso de mensajes garantiza que solo el hilo de la interfaz de usuario accede y modifica la interfaz gráfica, evitando problemas de concurrencia y corrupción de la interfaz, y manteniendo la consistencia y la capacidad de respuesta de la interfaz de usuario, incluso en aplicaciones complejas con múltiples hilos trabajando en segundo plano.

La comunicación entre hilos a través de paso de mensajes presenta también ventajas y desventajas que debemos considerar al elegir este mecanismo de comunicación en nuestros programas multihilo

Entre las ventajas destacamos una mayor seguridad y robustez frente a errores de concurrencia, un mayor aislamiento entre hilos, y su facilidad de programación y depuración. Sin embargo también presenta desventajas, como por ejemplo una menor eficiencia y rendimiento en comparación con la memoria compartida, una mayor sobrecarga (_overhead_) y menor flexibilidad para compartir datos complejos.

En resumen, el paso de mensajes es una técnica de comunicación más segura y robusta que la memoria compartida, pero puede ser menos eficiente en términos de rendimiento. La elección entre memoria compartida y paso de mensajes dependerá de los requisitos específicos de cada aplicación, priorizando el rendimiento en algunos casos y la seguridad y la facilidad de programación en otros.

## 9. Patrones de concurrencia y trabajo con hilos en Java

En el desarrollo de software concurrente, la mera creación de hilos no es suficiente. Una gestión desestructurada de la concurrencia puede conducir a sistemas frágiles, difíciles de depurar y plagados de errores sutiles como las condiciones de carrera (_race conditions_), el interbloqueo (_deadlock_) o la inanición (_starvation_). Para abordar esta complejidad, la ingeniería de software se apoya en **patrones de diseño de concurrencia**, que son soluciones probadas y reutilizables a problemas comunes en entornos multihilo.

Estos patrones nos ofrecen un vocabulario común y un marco conceptual para razonar sobre la organización de las tareas y la comunicación entre hilos. A continuación, profundizaremos en tres patrones fundamentales que todo desarrollador en Java debe conocer: **Jefe-Trabajador** (_Master-Worker_), **Equipo de trabajo** (_Work team_) y **Línea de Ensamblado** (_Pipeline_).

### 9.1 Patrón jefe-trabajador (Master-Worker)

Este patrón, también conocido como _Master-Slave_, se basa en una estructura jerárquica y es uno de los modelos de concurrencia más extendidos por su simplicidad y eficacia. La idea central es la separación de responsabilidades: un único hilo, el **jefe** (_master_), se encarga de la coordinación y distribución del trabajo, mientras que un grupo de hilos **trabajadores** (_workers_) se dedica exclusivamente a la ejecución de las tareas.

El flujo de trabajo se inicia cuando el hilo **jefe** recibe una carga de trabajo completa, que puede ser, por ejemplo, una lista de archivos para procesar o un conjunto de peticiones de red. La primera responsabilidad del jefe es descomponer este trabajo en unidades más pequeñas, discretas e independientes, denominadas tareas. A continuación, deposita estas tareas en una estructura de datos compartida, que típicamente es una **cola bloqueante** (`BlockingQueue`).

Los hilos **trabajadores**, que conforman un _pool_ o grupo, operan en un bucle simple: solicitan una tarea de la cola, la ejecutan y, una vez finalizada, vuelven a la cola para solicitar la siguiente. El uso de una cola bloqueante simplifica enormemente la sincronización, ya que un trabajador que intente tomar una tarea de una cola vacía quedará bloqueado automáticamente hasta que el jefe añada una nueva.

![Patrón jefe-trabajador (_Master-Worker_)](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/master_worker_pattern.png)
*Patrón jefe-trabajador (_Master-Worker_)*

La principal ventaja de este patrón es el **balanceo de carga dinámico**. Dado que los trabajadores toman tareas de una cola común, aquellos que terminan más rápido (ya sea porque son más eficientes o porque les tocaron tareas más cortas) se pondrán a trabajar inmediatamente en la siguiente tarea disponible. Esto maximiza la utilización de la CPU y es especialmente eficaz cuando las tareas son heterogéneas, es decir, de duración y complejidad variables. Este modelo se enmarca dentro del **paralelismo de tareas**, ya que el foco está en distribuir diferentes tareas, que pueden ser funcionalmente distintas, entre los hilos.

Sin embargo, el patrón no está exento de inconvenientes. El hilo jefe puede convertirse en un **cuello de botella** si la tarea de dividir y distribuir el trabajo es computacionalmente costosa. Además, la cola de tareas compartida es un punto de contención central: con un número muy elevado de trabajadores, el acceso concurrente a la cola puede degradar el rendimiento.

En Java, rara vez se implementa este patrón desde cero. El framework `ExecutorService`, parte del paquete `java.util.concurrent`, y que estudiaremos más adelante, es la encarnación canónica del patrón Jefe-Trabajador. El `ExecutorService` actúa como el "jefe", gestionando un _pool_ de hilos y una cola interna de tareas. Nosotros, como programadores, simplemente creamos un `ExecutorService` y le enviamos tareas (`Runnable` o `Callable`) a través del método `submit()`. El `ExecutorService` se encarga de toda la complejidad de la gestión del ciclo de vida de los hilos y la asignación de tareas.

### 9.2 Patrón equipo de trabajo (Work team)

Este patrón adopta un enfoque diferente. En lugar de una jerarquía, tenemos un **equipo de hilos** iguales que colaboran para resolver un problema de gran envergadura. El principio subyacente es el **paralelismo de datos**, una estrategia de "divide y vencerás" aplicada a los datos. El conjunto de datos masivo se divide en fragmentos, y cada hilo del equipo se hace responsable de procesar uno de esos fragmentos.

La característica distintiva de este patrón es la **partición estática del trabajo**. Antes de que comience el procesamiento, el conjunto de datos se divide. Por ejemplo, si se debe aplicar un filtro a una imagen de 4000x4000 píxeles con un equipo de 8 hilos, se podría asignar a cada hilo una franja horizontal de 500x4000 píxeles. Todos los hilos ejecutan el mismo código, pero sobre su subconjunto exclusivo de datos.

![Patrón equipo de trabajo (_Work team_)](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/work_team_pattern.png)
*Patrón equipo de trabajo (_Work team_)*

La gran ventaja es la **mínima sobrecarga de coordinación**. Una vez que el trabajo ha sido distribuido, los hilos operan de manera mayormente independiente, sin necesidad de competir por una cola de tareas compartida. Esto reduce drásticamente la contención y puede ofrecer un rendimiento excelente para problemas que se ajustan bien a este modelo, como los cálculos científicos, el renderizado de gráficos o el procesamiento de grandes arrays.

Sin embargo, su principal debilidad es el riesgo de **desbalanceo de carga**. Si la complejidad computacional de los datos no es uniforme, algunos hilos pueden terminar su trabajo mucho antes que otros. Por ejemplo, al procesar un genoma, algunas secciones pueden ser más repetitivas y requerir más análisis. Los hilos que terminen pronto permanecerán inactivos, esperando al hilo más lento, lo que limita la eficiencia global del sistema. Al final del proceso, es casi siempre necesario un punto de **sincronización** (una barrera) donde el hilo principal espera a que todos los miembros del equipo terminen para poder combinar sus resultados parciales en una solución final.

Aunque se puede implementar manualmente, Java ofrece abstracciones más potentes para el paralelismo de datos. El **Framework Fork/Join**, introducido en Java 7, es una implementación sofisticada de este patrón que utiliza una estrategia de _work-stealing_ (robo de trabajo) para mitigar el desbalanceo de carga: los hilos que terminan su trabajo pueden "robar" tareas de la cola de otros hilos que todavía están ocupados.

A un nivel aún más alto, los **streams paralelos** (introducidos en Java 8) utilizan el framework Fork/Join por debajo y permiten paralelizar operaciones sobre colecciones con un simple cambio de método: de `stream()` a `parallelStream()`.

### 9.3 Patrón línea de ensamblado (Pipeline)

Inspirado en las cadenas de montaje industriales, el patrón de línea de ensamblado o _pipeline_ organiza el procesamiento en una secuencia de **etapas**. Cada etapa es gestionada por uno o más hilos y se especializa en una parte del trabajo total. La salida de una etapa se convierte en la entrada de la siguiente, permitiendo que múltiples elementos de datos se procesen simultáneamente en diferentes puntos de la cadena.

Imaginemos un proceso de transformación de datos con tres fases: leer desde disco, comprimir y enviar por red. En un modelo _pipeline_, tendríamos al menos tres hilos: uno para cada fase. Estos hilos se comunican a través de **buffers intermedios**, que en Java se implementan perfectamente con `BlockingQueue`. El primer hilo lee un bloque de datos y lo encola en el primer buffer. El segundo hilo lo toma, lo comprime y lo encola en el segundo buffer. El tercer hilo lo toma y lo envía por la red.

![Patrón línea de ensamblado (Pipeline)](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/pipeline_pattern.png)
*Patrón línea de ensamblado (Pipeline)*

La gran ventaja de este patrón es el aumento del **rendimiento global** (_throughput_). Aunque la latencia para un único dato (el tiempo que tarda en recorrer toda la cadena) no disminuye, la capacidad del sistema para procesar datos por segundo aumenta drásticamente, ya que mientras un hilo envía el dato N, otro puede estar comprimiendo el dato N+1 y un tercero leyendo el dato N+2.

Las colas bloqueantes entre etapas son cruciales porque **desacoplan** los hilos. Si la etapa de compresión es temporalmente más lenta, el buffer de entrada se llenará. Una vez lleno, el hilo de lectura que intente añadir un nuevo dato (`put()`) se bloqueará. Este mecanismo, conocido como **contrapresión** (_back-pressure_), regula de forma natural el flujo a través del _pipeline_, evitando que una etapa rápida desborde a una más lenta y agote la memoria.

El desafío principal en el diseño de un _pipeline_ es **balancear las etapas**. La velocidad de toda la línea de ensamblado está limitada por su componente más lento (la "etapa cuello de botella"). Optimizar el rendimiento del sistema a menudo implica identificar y mejorar esa etapa específica, quizás asignándole más hilos.

La implementación en Java se basa en hilos que ejecutan bucles infinitos y se comunican a través de `BlockingQueue`. Un aspecto crítico es cómo detener el _pipeline_ de forma ordenada. Una técnica común es la _"poison pill"_ (píldora venenosa): cuando la primera etapa (el productor) termina de generar datos, inserta un objeto centinela especial en la cola. Cada etapa, al recibir esta "píldora", sabe que no llegarán más datos, por lo que debe terminar su trabajo pendiente, propagar la píldora a la siguiente etapa y finalizar su ejecución.

## Esquema

| Concepto | Idea clave |
|---|---|
| Proceso | Unidad de reserva de memoria y de protección del SO (PCB) |
| Hilo | Unidad de ejecución dentro de un proceso (TCB); comparte código, datos y _heap_ |
| Cambio de contexto | Entre hilos es más barato que entre procesos (no cambia el espacio de direcciones) |
| Linux / Windows | Linux: hilos = procesos ligeros con PID propio y TGID común · Windows: `EPROCESS` + `ETHREAD` |
| Unidad de planificación | El **hilo**, no el proceso |
| Estados | Nuevo → Listo ⇄ Corriendo → Bloqueado / Suspendido / Suspendido por tiempo → Terminado |
| Comunicación | Objetos compartidos (rápido, exige sincronización) o paso de mensajes (seguro, más lento) |
| Patrones | Jefe-trabajador (`ExecutorService`) · Equipo de trabajo (Fork/Join) · Pipeline (`BlockingQueue`) |
