## 1. Gestión de procesos en multiprogramación

La gestión de procesos es una de las funciones más importantes y complejas del SO: en multiprogramación, el SO actúa como **director de orquesta** — crea, administra, ejecuta y finaliza procesos de manera eficiente y justa.

> [!note] Proceso vs. hilo
> Un **proceso** es una instancia de un programa en ejecución (código, datos, espacio de direcciones y recursos asignados por el SO). Un **hilo** es la **unidad mínima de ejecución dentro de un proceso**: todo proceso tiene al menos un hilo y puede tener varios (multihilo).

El SO mantiene una **tabla de procesos** (tabla de descriptores de proceso) con información detallada de cada proceso activo.

### 1.1 El cargador de procesos

Al lanzar un ejecutable, el **cargador de procesos** del SO crea el proceso:

1. Crea y configura un **espacio de direcciones de memoria virtual** en RAM: asocia (mapea) el código del ejecutable de disco y reserva espacio para datos, pila de llamadas y otros segmentos.
2. Es **virtual**: el proceso percibe una zona de memoria contigua y exclusiva, aunque físicamente esté fragmentada y no corresponda directamente a la RAM física.
3. Crea el **PCB** (ver 1.2) y sitúa el proceso en la **cola de listos**.

Proceso en memoria — los segmentos:

| Segmento | Contenido |
| --- | --- |
| **Código (Texto)** | Instrucciones del programa |
| **Datos** | Variables globales, datos estáticos |
| **Pila (Stack)** | Pila de llamadas a funciones, variables locales |
| **Heap (Montón)** | Memoria dinámica asignada en tiempo de ejecución |

![[proceso_memoria.png]]

### 1.2 El PCB (Process Control Block)

> [!definition] PCB
> Bloque de Control de Proceso: estructura de datos con la información única de cada proceso — el "DNI del proceso" para el SO. Permite controlarlo a lo largo de su ciclo de vida y la usa el planificador para decidir qué proceso ejecutar.

Contenido:

| Campo | Qué guarda |
| --- | --- |
| **PID** | Identificador entero único del proceso |
| **Estado actual** | En ejecución, listo, bloqueado/en espera, suspendido, finalizando |
| **Espacio de direcciones** | Punteros al inicio y tamaño de la zona de memoria virtual reservada |
| **Información de planificación** | Prioridad, quantum asignado, estadísticas de uso de CPU |
| **Información para el cambio de contexto** | Contador del programa (PC), estado de los registros de la CPU, puntero de pila (Stack Pointer) |
| **Gestión de memoria** | Tablas de páginas u otra información de memoria virtual |
| **Recursos utilizados** | Ficheros abiertos, conexiones de red, dispositivos E/S asignados |

> [!note] La ejecución siempre es desde RAM
> Para ejecutar, código y datos (o la parte activa) deben estar cargados en la memoria RAM física. El SO mueve datos entre RAM y disco con técnicas de memoria virtual, pero las instrucciones siempre se ejecutan desde RAM.

> [!warning] Protección de memoria
> El proceso está **confinado a su espacio de direcciones**: si intenta acceder fuera, el SO detecta la violación y genera una excepción — *segmentation fault* (Unix/Linux) o *error de protección general* (Windows, los antiguos "pantallazos azules"). Este mecanismo evita que un proceso erróneo o malicioso corrompa la memoria de otros procesos o del propio SO.

### 1.3 Ciclo de reparto de la CPU

- Los procesos nuevos cargados entran en la **cola de procesos listos** (*ready queue*), esperando turno.
- Al llegar su turno, el SO concede el núcleo a un hilo del proceso durante un tiempo limitado y equitativo: **quantum** o *time slice*.
- Al expirar el quantum o bloquearse el proceso (p. ej. por E/S), el planificador elige el siguiente de la cola de listos, y el ciclo se repite — así se logra la multiprogramación.
- Un proceso puede perder el procesador **antes** de agotar el quantum si debe esperar una entrada del usuario, una lectura/escritura en disco o un dato de otro proceso; cuando termina su espera vuelve a la cola de preparados.

## 2. Estados de un proceso

A lo largo de su vida un proceso pasa por distintos estados. El diagrama es una visión **general y simplificada**: la nomenclatura y el número exacto varían según el SO, pero el modelo conceptual básico es similar.

![[estados_proceso.png]]

### 2.1 Los estados

| Estado | Significado |
| --- | --- |
| **Nuevo** (*new*) | El proceso está siendo creado: el SO configura memoria, espacio de direcciones y PCB. Aún no se ha ejecutado |
| **Listo** (*ready*) | Preparado para ejecutarse, esperando que el planificador le asigne un núcleo. Todos los recursos asignados **excepto la CPU**. Está en la cola de listos |
| **En ejecución** (*running*) | Ejecutándose activamente en la CPU. Monoprocesador: sólo uno a la vez. Multiprocesador: varios, uno por núcleo |
| **Bloqueado** (*blocked*) | No puede continuar hasta que termine una operación de E/S u otro evento externo. Incluye el estado *esperando* (*waiting*): bloqueado por un recurso compartido (semáforo, mutex, monitor). Sigue cargado en RAM |
| **Suspendido** (*suspended*) | Movido temporalmente de RAM a disco mediante **swapping**, para liberar memoria. No puede competir por la CPU ni hacer E/S. Puede ser *suspendido bloqueado* (venía de bloqueado) o *suspendido listo* (venía de listo, menos frecuente) |
| **Terminado** (*terminated*) | Ha finalizado (con éxito o por error). Deja de ejecutarse y el SO libera sus recursos **poco a poco**: la información de salida (código de retorno) sigue en el PCB hasta que el **proceso padre** la recoge. Mientras ocupa entrada en la tabla de procesos se llama **zombie** / proceso zombi |

> [!tip] Por qué existe "bloqueado"
> Las operaciones de E/S son mucho más lentas que la CPU: mientras un proceso espera, se le retira el procesador y se asigna a otros, optimizando su uso.

> [!note] Zombis (Unix/Linux/macOS)
> Proceso que ya terminó pero mantiene su entrada en la tabla de procesos hasta que su padre "recolecta" su estado/código de retorno.

### 2.2 Las transiciones

| Transición | De → A | Qué la provoca |
| --- | --- | --- |
| **Asignación** (*dispatching*) | listo → en ejecución | El planificador asigna un núcleo a un proceso listo (según el algoritmo: prioridad, tiempo de espera…) |
| **Apropiación / interrupción** (*preemption*) | en ejecución → listo | Agota el quantum o llega un proceso de mayor prioridad: el SO interrumpe, guarda el contexto y devuelve el proceso a la cola de listos |
| **Terminación** (*termination*) | en ejecución → terminado | El proceso acaba de forma normal o por error y libera sus recursos |
| **Espera** (*event wait*) | en ejecución → bloqueado | Necesita una E/S o esperar un evento (liberación de recurso, señal…) y cede la CPU **voluntariamente** |
| **Espera completada** (*event completion*) | bloqueado → listo | El dispositivo/recurso notifica al SO que el evento ocurrió; el proceso vuelve a la cola de listos |
| **Suspensión** (*suspension*) | RAM → disco | El SO necesita liberar RAM. Habitual desde *bloqueado* (bloqueado suspendido: no usa CPU y espera un evento, es buen candidato); menos habitual desde *listo* (suspensión "voluntaria" del SO, último recurso por escasez de memoria) |
| **Reactivación** (*resume*) | disco → RAM | Se ha liberado memoria, el proceso tiene mayor prioridad, o el evento que lo bloqueaba se completó. Pasa a *Listo*; si estaba suspendido bloqueado, no se reactiva hasta que el evento se complete |

> [!example]- Ejercicios
> 1. Dibuja el diagrama de estados y explica cada estado y transición con tus palabras.

## 3. Planificación de procesos

El **kernel** (núcleo) del SO se encarga de la funcionalidad básica: es el responsable de la gestión de los recursos, se accede a él mediante **llamadas al sistema**, es la parte más pequeña del sistema comparada con la interfaz. El resto del SO son los **programas del sistema**.

Todos los programas se ejecutan como conjunto de procesos: el SO decide **pausar** la ejecución (p. ej. por llevar mucho tiempo en la CPU) y **cuál es el siguiente** proceso. Almacena una tabla con los procesos cargados — una entrada por proceso que apunta a su PCB:

![[process_control_blocks.gif]]

> [!definition] Scheduler (planificador)
> Componente del SO que decide en cada instante qué proceso de la cola de "listos" debe asignarse a la CPU para su ejecución, y durante cuánto tiempo (quantum).

Para planificar, el SO organiza los procesos en **colas** y los va pasando de una a otra según su estado:

- **Cola de procesos**: todos los procesos del sistema.
- **Cola de preparados**: todos los listos esperando ejecutarse.
- **Varias colas de dispositivos**: procesos esperando alguna operación de E/S.

![[process_queues.gif]]

| Tipo de planificación | Función | Frecuencia |
| --- | --- | --- |
| **Corto plazo** | Selecciona procesos de la cola de preparados para pasarlos a ejecución. Opciones: *sin desalojo* (sólo sale si termina o se bloquea), *apropiativa* (sale si termina, se bloquea o llega uno de mayor prioridad), *tiempo compartido* (desalojo cada quantum, todos con la misma prioridad) | Muy frecuente (milisegundos) → algoritmo muy sencillo |
| **Largo plazo** | Selecciona qué procesos nuevos pasan a la cola de preparados; controla el **grado de multiprogramación** | Menos frecuente |

### 3.1 Algoritmos de planificación

La estrategia del planificador es el **algoritmo de planificación**. No existe un algoritmo "perfecto": elegir implica **compromiso** (*trade-off*) porque algunos objetivos son conflictivos.

Objetivos que se busca conciliar:

| Objetivo | Qué busca |
| --- | --- |
| **Eficacia / utilización de la CPU** | Mantener la CPU ocupada ≈100%, sin *idle time* |
| **Equidad / justicia** | Todos los procesos con oportunidad justa; evitar la inanición (*starvation*) |
| **Tiempo de respuesta** | Minimizar el tiempo desde la acción del usuario hasta la primera respuesta (clave en sistemas interactivos) |
| **Tiempo de finalización** | Minimizar el tiempo total del proceso desde que inicia hasta terminar (relevante en *batch*) |
| **Rendimiento / throughput** | Maximizar tareas completadas por unidad de tiempo |

Algoritmos comunes:

| Algoritmo | Funcionamiento | Puntos fuertes / débiles |
| --- | --- | --- |
| **FIFO / FCFS** | El primero que llega a la cola de listos es el primero en ejecutarse | Sencillo, pero procesos cortos esperan mucho si llega uno largo |
| **Round Robin (RR)** | Asigna un **quantum** a cada proceso de forma rotatoria; si no termina, se expulsa y pasa al siguiente (circular) | Mejora el tiempo de respuesta interactivo; quantum muy pequeño → mucha sobrecarga de cambios de contexto |
| **SJF** (Shortest Job First) | Ejecuta el de tiempo estimado **más corto** primero | Minimiza el tiempo de finalización medio; requiere conocer/estimar el tiempo — no siempre posible |
| **Por prioridades** | Siempre el proceso listo de mayor prioridad | Prefiere procesos críticos; puede causar *starvation* de baja prioridad |
| **Multinivel** | Combina algoritmos para distintos tipos de procesos o colas de prioridad; en Windows y macOS los procesos nuevos entran con máxima prioridad y **se degradan de cola** conforme se ejecutan | Más flexibilidad; favorece procesos cortos e interactivos |

### 3.2 El dispatcher

> [!definition] Dispatcher
> Módulo del planificador que realiza el **cambio de contexto** (conmutación de procesos): retira la CPU al proceso en ejecución y se la asigna al elegido por el planificador.

- El **scheduler decide** y el **dispatcher ejecuta** la decisión.
- Cuando un proceso pierde el procesador, su estado de ejecución debe **preservarse** (en el PCB) para continuar exactamente en el "punto" y con el "estado" en que estaba.
- La **latencia del cambio de contexto** (*dispatch latency*) es el tiempo que dura la operación: durante él la CPU no ejecuta instrucciones útiles. Debe ser lo más rápido posible; una latencia excesiva degrada el rendimiento global (quanta pequeños o alta frecuencia de cambios).

> [!tip] Procesos críticos
> Los procesos del SO (gestión de memoria, el propio planificador, controladores de dispositivos, servicios de red y de usuarios) tienen **prioridad más alta** que los de usuario, para que el sistema no se vuelva inestable.

## 4. Herramientas de gestión de procesos

Todo SO con interfaz gráfica tiene una aplicación de monitorización y gestión de procesos: **Administrador de tareas** (Windows), **Monitor del sistema** / `gnome-system-monitor` (Linux), **Monitor de Actividad** (macOS). Funcionalidades comunes:

- **Listado detallado de procesos activos**: nombre, PID, usuario propietario, ruta del ejecutable, en tiempo real.
- **Finalizar procesos** (forzar cierre / "matar"): útil con aplicaciones que no responden, con precaución (puede provocar pérdida de datos o inestabilidad).
- **Información de uso de recursos** por proceso y global: CPU (%), RAM y memoria virtual (intercambio en disco), red (ancho de banda, conexiones), disco (lectura/escritura) — para detectar procesos que consumen de más y diagnosticar rendimiento.
- **Modificar la prioridad** de ejecución de un proceso (suele requerir permisos de administrador).

GUI vs. CLI:

| Característica | Herramientas GUI | Herramientas CLI |
| --- | --- | --- |
| Interfaz | Visual, intuitiva, ratón y menús | Textual, comandos y sintaxis |
| Curva de aprendizaje | Baja | Más alta |
| Funcionalidad | Básica/intermedia, suficiente para lo común | Mayor potencia y flexibilidad, tareas avanzadas |
| Automatización | Limitada | Ideal (shell scripts, batch) |
| Acceso remoto | Requiere escritorio remoto | Ideal (SSH o terminal) |
| Consumo de recursos | Mayor (interfaz gráfica) | Menor, muy eficiente |
| Mejor para | Principiantes, monitorización general, tareas puntuales | Administradores, usuarios avanzados, automatización, remoto |

### 4.1 Comandos en Windows

| Comando | Uso |
| --- | --- |
| `tasklist` | Lista los procesos del sistema: ejecutable, PID, sesión, nº de sesión, memoria (KB). Filtros y formatos (tabla, lista, CSV) → `tasklist /?` |
| `taskkill` | Finaliza procesos: `taskkill /PID <pid>` o por imagen `taskkill /IM <nombre>`; `/F` fuerza el cierre (con precaución) → `taskkill /?` |

### 4.2 Comandos en Linux

| Comando | Uso |
| --- | --- |
| `ps` | Lista procesos; sin opciones, los del usuario en la sesión actual. `ps aux` = todos los del sistema (**a** todos los usuarios, **u** info del usuario propietario, **x** sin terminal de control — demonios) → `man ps` |
| `pstree` | Árbol jerárquico de procesos con relaciones padre/hijo. `pstree -AGu`: líneas guía + usuario propietario → `man pstree` |
| `kill` | Envía **señales** a un proceso por PID. `kill -9 <PID>` = SIGKILL, terminación incondicional (sin limpieza: riesgo de pérdida/corrupción de datos). `kill <PID>` = SIGTERM (15), terminación controlada y liberación adecuada de recursos → `man kill` |
| `killall` | Mata procesos **por nombre de ejecutable**: `killall <app>` — termina **todas** las instancias con ese nombre → `man killall` |
| `nice` | Ejecuta un programa con prioridad modificada: `nice -n <nivel> <comando>`. 0 = normal; positivos hasta **19** = menor prioridad; negativos hasta **-20** = mayor prioridad (requiere administrador). Sólo afecta a procesos **nuevos**; para cambiar la prioridad de uno en ejecución, `renice` → `man nice`, `man renice` |

## Esquema

- **Cargador de procesos**: crea el espacio de direcciones virtual (código, datos, pila, heap) + PCB, y deja el proceso en cola de listos.
- **PCB** = DNI del proceso: PID, estado, direcciones, prioridad/quantum, contexto (PC, registros, SP), memoria, recursos.
- **Confinamiento** a su espacio de direcciones → segmentación fault / protección general.
- Estados: **nuevo → listo → en ejecución → terminado**, con **bloqueado** (espera E/S o recurso) y **suspendido** (swapping a disco, listo o bloqueado); *zombie* = terminado esperando que el padre recoja su estado.
- Transiciones: asignación, apropiación, terminación, espera, espera completada, suspensión, reactivación.
- **Scheduler** (corto/largo plazo) decide + **dispatcher** ejecuta el cambio de contexto; *dispatch latency*.
- Algoritmos: FIFO, Round Robin (quantum), SJF, prioridades, multinivel — siempre con compromiso entre eficacia, equidad, respuesta, finalización y throughput.
- Herramientas: GUI (Administrador de tareas, Monitor del sistema, Monitor de Actividad) vs. CLI (`tasklist`/`taskkill`, `ps`/`pstree`/`kill`/`killall`/`nice`).
