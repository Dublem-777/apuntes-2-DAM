## 1. Comunicación de tareas

Para que las distintas tareas que componen un programa concurrente puedan cooperar y coordinarse para lograr un objetivo común, es fundamental que puedan comunicarse e intercambiar información entre sí. Existen dos modelos o paradigmas principales para la comunicación entre tareas concurrentes.

### 1.1 Memoria compartida y paso de mensajes

> [!definition] Comunicación a través de memoria compartida
> Las tareas concurrentes (normalmente hilos dentro de un mismo proceso) comparten una región de memoria principal que es accesible por todas ellas y que se utiliza como espacio común para el intercambio de datos.

La comunicación a través de memoria compartida es **habitual y eficiente cuando las tareas se están ejecutando dentro del mismo ordenador o sistema**, ya que el acceso a la memoria principal suele ser relativamente rápido. Sin embargo, la principal desventaja de la memoria compartida es que requiere mecanismos de sincronización de acceso a datos para evitar condiciones de carrera y problemas de visibilidad de datos, como hemos visto en apartados anteriores. La sincronización es imprescindible en este modelo para garantizar la coherencia y la integridad de los datos compartidos y para coordinar el acceso concurrente a la memoria compartida por parte de múltiples tareas. Este modelo de comunicación es típico en la programación multihilo dentro de un mismo proceso, donde los hilos comparten el mismo espacio de memoria del proceso.

> [!definition] Comunicación a través de paso de mensajes
> Las tareas concurrentes (que pueden ser procesos o hilos, y pueden estar ejecutándose en el mismo ordenador o en ordenadores distintos) se comunican enviándose mensajes entre sí a través de un canal de comunicación. Cada tarea tiene su propio espacio de memoria privado, y la comunicación se realiza de forma explícita mediante operaciones de envío y recepción de mensajes.

El paso de mensajes es especialmente adecuado y frecuente cuando las tareas se están ejecutando en ordenadores distintos o en sistemas distribuidos, donde no existe una memoria física compartida directamente accesible por todas las tareas. Una de las ventajas del paso de mensajes es que la sincronización suele ser implícita en las propias operaciones de envío y recepción de mensajes, lo que puede simplificar la programación concurrente en algunos casos y reducir la necesidad de mecanismos de sincronización explícitos (aunque la sincronización a nivel lógico y de coordinación de tareas sigue siendo necesaria). Este modelo de comunicación es **típico en la programación multiproceso** (donde los procesos tienen espacios de memoria separados) **y en sistemas distribuidos**, donde la comunicación entre nodos se realiza a través de la red.

| | Memoria compartida | Paso de mensajes |
| --- | --- | --- |
| Tareas típicas | Hilos de un mismo proceso | Procesos o hilos, en la misma máquina o en máquinas distintas |
| Memoria | Región común accesible por todas | Espacio privado por tarea |
| Sincronización | **Explícita** e imprescindible (condiciones de carrera, visibilidad) | Suele ser **implícita** en el envío/recepción |
| Dónde encaja | Mismo ordenador: rápida y eficiente | Multiproceso y sistemas distribuidos |

### 1.2 Implementación del paso de mensajes

El **intercambio de mensajes** entre tareas concurrentes se puede implementar utilizando diferentes mecanismos y tecnologías, dependiendo del contexto y de las necesidades de la aplicación. Dos de las formas más comunes de implementar el paso de mensajes son:

- **Utilizar un buffer de memoria (o cola de mensajes)**: En este caso, se crea un canal de comunicación intraproceso o interproceso utilizando una **estructura de datos compartida en memoria principal**, que actúa como un buffer o una cola donde los procesos o hilos pueden depositar (enviar) mensajes y de donde otros procesos o hilos pueden extraer (recibir) mensajes. Este buffer de memoria puede ser una cola FIFO (primero en entrar, primero en salir), una pila LIFO (último en entrar, primero en salir), o cualquier otra estructura de datos adecuada para el intercambio de mensajes. Cuando se utiliza un buffer de memoria compartido, es importante proteger el acceso al buffer con mecanismos de sincronización de acceso a datos (exclusión mutua) para evitar condiciones de carrera en las operaciones de encolado y desencolado de mensajes. Este mecanismo es eficiente para la comunicación entre tareas que se ejecutan en el mismo ordenador y comparten memoria, y es la base de muchas implementaciones de colas de mensajes y canales de comunicación en sistemas operativos y bibliotecas de concurrencia. Ejemplos de uso de buffers de memoria para paso de mensajes son: comunicación entre hilos en Java utilizando `BlockingQueue`, canales en Go, o colas de mensajes en sistemas operativos.
- **Utilizar sockets de red (o comunicación en red)**: Los sockets son un mecanismo fundamental para el intercambio de información entre procesos que se ejecutan en máquinas distintas, conectadas a través de una red de comunicaciones (como una red local o Internet). Los sockets utilizan protocolos de red (como TCP/IP o UDP) para la transmisión de mensajes a través de la red. La comunicación basada en sockets es esencial para construir sistemas distribuidos y aplicaciones cliente-servidor, donde diferentes componentes del sistema se ejecutan en máquinas separadas y necesitan comunicarse entre sí a través de la red. Ejemplos de uso de sockets para paso de mensajes son: comunicación entre un servidor web y un cliente web, comunicación entre microservicios en una arquitectura distribuida, o comunicación en aplicaciones peer-to-peer.

> [!definition] Socket
> Punto final de comunicación en una red, a través del cual un proceso puede enviar y recibir datos a otro proceso en otra máquina (o en la misma máquina).

> [!warning] La cola de mensajes también necesita exclusión mutua
> Aunque sea paso de mensajes, si el buffer está en **memoria compartida**, encolar y desencolar son operaciones sobre un recurso compartido: hay que protegerlas para evitar condiciones de carrera.

> [!tip] En resumen
> Tanto la memoria compartida como el paso de mensajes son modelos válidos y ampliamente utilizados para la comunicación entre tareas concurrentes, pero presentan características y compromisos diferentes. La memoria compartida suele ser más eficiente en términos de rendimiento y latencia para la comunicación intraproceso en sistemas con memoria compartida, pero requiere una gestión cuidadosa de la sincronización explícita para evitar errores de concurrencia. El paso de mensajes, por otro lado, es más adecuado para sistemas distribuidos y para la comunicación interproceso o intermáquina, donde no hay memoria física compartida, y simplifica la sincronización en algunos aspectos al ser implícita en el envío y recepción de mensajes, pero puede introducir una mayor latencia y sobrecarga de comunicación debido a la necesidad de serializar y deserializar mensajes y transmitirlos a través de la red.
>
> La elección del modelo de comunicación más adecuado dependerá del tipo de sistema concurrente que se esté construyendo, de los requisitos de rendimiento, de la complejidad de la sincronización, y de las herramientas y tecnologías disponibles. En muchos sistemas complejos, se pueden utilizar combinaciones de ambos modelos, utilizando memoria compartida para la comunicación eficiente dentro de un mismo proceso y paso de mensajes para la comunicación entre procesos o máquinas.

## 2. Tipos de comunicación

### 2.1 Elementos de la comunicación

Para comprender mejor las diferentes formas en que las tareas concurrentes pueden comunicarse, es útil analizar los elementos básicos que intervienen en cualquier proceso de comunicación. En toda comunicación, podemos identificar los siguientes componentes fundamentales:

- **Mensaje**: Es la información o los datos que se transmiten entre el emisor y el receptor. El mensaje es el objeto fundamental de la comunicación, y puede contener cualquier tipo de información relevante para las tareas concurrentes (datos, órdenes, señales, etc.).
- **Emisor**: Es la entidad (proceso, hilo, tarea) que inicia la comunicación y envía o genera el mensaje. El emisor es el origen de la información que se quiere transmitir.
- **Receptor**: Es la entidad (proceso, hilo, tarea) que recibe o recoge el mensaje enviado por el emisor. El receptor es el destino de la información y quien la procesa o utiliza.
- **Canal**: Es el medio o la vía a través de la cual viaja o se transmite el mensaje desde el emisor hasta el receptor. El canal es el soporte físico o lógico de la comunicación, y puede ser un cable, una red, una memoria compartida, etc.

### 2.2 Según el canal

Podemos clasificar el canal de comunicación en función de su capacidad para transmitir información en uno o ambos sentidos, y de la simultaneidad en la transmisión:

- **Simplex** (unidireccional o símplex): En un canal símplex, la comunicación se produce en una única dirección o sentido. La información fluye siempre desde el emisor hacia el receptor, pero no en sentido contrario. El emisor actúa únicamente como fuente de mensajes, y el receptor únicamente como destino o "escucha" del mensaje al final del canal. Ejemplo clásico: la radiodifusión (una emisora de radio transmite señales, y los receptores de radio solo pueden recibir la señal, no enviar mensajes de vuelta) o la reproducción de una película en una sala de cine (el proyector emite la película, y el público solo la recibe, sin interactuar con el proyector). Símil: una calle de dirección única, donde el tráfico solo puede circular en un sentido.
- **Full duplex** (bidireccional o dúplex completo): En un canal full duplex, la comunicación puede viajar en ambos sentidos (desde el emisor hacia el receptor, y desde el receptor hacia el emisor) de forma simultánea. Ambas entidades (emisor y receptor) pueden transmitir y recibir mensajes al mismo tiempo, estableciendo una comunicación bidireccional completa. Ejemplo típico: las comunicaciones telefónicas (ambas personas pueden hablar y escuchar simultáneamente) o las videoconferencias. Símil: una avenida de doble sentido con carriles separados, donde el tráfico puede circular en ambas direcciones al mismo tiempo sin interferencia.
- **Half duplex** (semibidireccional o semidúplex): En un canal half duplex, la comunicación puede viajar en ambos sentidos (desde el emisor hacia el receptor, y viceversa), pero no al mismo tiempo. La transmisión es bidireccional, pero alternante en el tiempo. En un momento dado, solo una de las entidades puede transmitir, mientras que la otra debe escuchar o esperar su turno para transmitir. Ejemplo clásico: la comunicación con walkie-talkies (solo una persona puede hablar a la vez, mientras la otra escucha, y para responder hay que esperar a que la primera persona termine de hablar y pulse el botón para cambiar el sentido de la comunicación). Símil: una calle estrecha de un solo carril con tráfico en ambos sentidos, donde los coches deben esperar su turno para circular en una u otra dirección, sin poder circular simultáneamente en sentidos opuestos.

![Tipos de canales de comunicación](https://educacionadistancia.juntadeandalucia.es/centros/cadiz/pluginfile.php/242057/mod_resource/content/10/files/duplex.png)

*Tipos de canales de comunicación*

> [!warning] Half duplex ≠ full duplex
> Los dos son **bidireccionales**. La diferencia es la **simultaneidad**: half duplex va **por turnos** (walkie-talkie); full duplex, **a la vez** (teléfono).

### 2.3 Según la sincronía

Otra clasificación importante de la comunicación se basa en el grado de sincronía o acoplamiento temporal que se establece entre el emisor y el receptor durante el proceso de comunicación:

- **Comunicación síncrona** (o bloqueante): En la comunicación síncrona, el proceso emisor que envía un mensaje queda bloqueado o suspendido en su ejecución hasta que el proceso receptor recibe y procesa el mensaje. El emisor no puede continuar con su tarea hasta que se complete la operación de recepción por parte del receptor y, en algunos casos, hasta que reciba una respuesta o confirmación del receptor. Este tipo de comunicación implica una sincronización explícita entre el emisor y el receptor en el momento de la recepción del mensaje. Ejemplo: una llamada a una función o procedimiento síncrono en programación (el hilo que llama a la función se bloquea hasta que la función retorna un resultado). Analogía: una conversación cara a cara donde una persona espera a que la otra termine de escuchar y responder antes de continuar hablando.
- **Comunicación asíncrona** (o no bloqueante): En la comunicación asíncrona, el proceso emisor que envía un mensaje no se bloquea ni se suspende después de enviar el mensaje. El emisor continúa con su ejecución inmediatamente después de emitir el mensaje, sin esperar a que el receptor lo reciba o lo procese. La entrega del mensaje al receptor se realiza en segundo plano, de forma asíncrona con respecto a la ejecución del emisor. El receptor recibirá el mensaje en algún momento futuro, pero no hay una sincronización explícita en el momento del envío. Ejemplo: el envío de un correo electrónico (el emisor envía el correo y continúa trabajando, sin esperar a que el receptor lo lea o responda inmediatamente) o el envío de un mensaje a una cola de mensajes. Analogía: enviar una carta por correo postal: el emisor deposita la carta en el buzón y sigue con sus tareas, sin esperar confirmación inmediata de recepción.
- **Invocación remota** (o síncrona con respuesta): La invocación remota es un tipo de comunicación que combina aspectos de la comunicación síncrona y asíncrona, y que se utiliza típicamente en sistemas distribuidos y programación orientada a servicios (SOA) o microservicios. En la invocación remota, el proceso emisor (cliente) envía una solicitud o mensaje a un proceso receptor (servidor) que se encuentra en otra máquina (o en el mismo sistema, pero como un servicio separado). El proceso emisor queda suspendido o bloqueado temporalmente después de enviar la solicitud, esperando a recibir una respuesta o resultado del proceso receptor. Una vez que el proceso receptor recibe la solicitud, la procesa y envía una respuesta de vuelta al emisor. Cuando el emisor recibe la respuesta, se reanuda su ejecución. La invocación remota se considera síncrona desde el punto de vista del emisor, ya que se bloquea y espera una respuesta, pero la comunicación subyacente puede ser asíncrona y utilizar mecanismos de paso de mensajes en red. Ejemplo: una petición HTTP de un navegador web a un servidor web (el navegador envía la petición y espera la respuesta del servidor antes de mostrar la página web) o una llamada a un método o función de un objeto remoto en un sistema distribuido (RPC - Remote Procedure Call). Analogía: pedir comida a domicilio por teléfono: el cliente llama al restaurante (emisor envía solicitud), espera en la línea hasta que le confirman el pedido y le dan un tiempo de entrega (receptor procesa y envía respuesta), y solo entonces el cliente puede continuar con otras tareas sabiendo que la comida llegará. Después de la recepción de la respuesta, emisor y receptor pueden ejecutar síncronamente un segmento de código común si es necesario para completar la interacción, aunque esto no es siempre el caso en todas las formas de invocación remota. En algunos casos, la invocación remota puede ser unidireccional (sin respuesta esperada), acercándose más a la comunicación asíncrona.

La elección del tipo de sincronía en la comunicación (síncrona, asíncrona o invocación remota) tiene importantes implicaciones en el diseño y el comportamiento de los sistemas concurrentes:

| Tipo | Ventaja | Inconveniente |
| --- | --- | --- |
| **Síncrona** | Punto de sincronización claro entre emisor y receptor; facilita razonar sobre el flujo de control | Puede introducir bloqueos y reducir el paralelismo: el emisor espera a que el receptor termine |
| **Asíncrona** | Maximiza el paralelismo y la eficiencia: el emisor sigue trabajando | Más complejidad: gestionar la recepción en un momento futuro y coordinar las tareas |
| **Invocación remota** | Compromiso entre ambas; modelo solicitud-respuesta que facilita las aplicaciones cliente-servidor | Latencia de la red y complejidad de los entornos distribuidos |

La elección del tipo de sincronía más adecuado dependerá de los requisitos de la aplicación, del nivel de paralelismo deseado, de la complejidad de la sincronización que se pueda asumir, y del entorno de ejecución (sistema local o distribuido).

### 2.4 Según el rol de los interlocutores

Finalmente, podemos clasificar la comunicación en función del comportamiento o rol que asumen los interlocutores (procesos o tareas) que participan en la comunicación:

- **Comunicación simétrica** (o entre pares): En la comunicación simétrica, todos los procesos o tareas que participan en la comunicación tienen el mismo rol o comportamiento. Todos los interlocutores son iguales y pueden actuar tanto como emisores (enviando información) como receptores (recibiendo información). No hay una distinción jerárquica o funcional predefinida entre los participantes. Ejemplo: una conversación entre dos personas (ambas pueden preguntar y responder, iniciar y terminar la conversación) o una red peer-to-peer (P2P) donde todos los nodos pueden actuar como clientes y servidores. Analogía: una reunión o debate entre iguales, donde todos los participantes tienen voz y voto y pueden contribuir a la discusión.
- **Comunicación asimétrica** (o cliente-servidor): En la comunicación asimétrica, se establece una distinción clara de roles o comportamientos entre los interlocutores. Uno o varios procesos actúan como emisores o clientes, iniciando la comunicación y solicitando servicios o información. Otro proceso (o conjunto de procesos) actúa como receptor o servidor, escuchando las peticiones de los clientes y respondiendo a ellas, proporcionando los servicios o la información solicitada. En este modelo, la comunicación es principalmente dirigida desde los clientes hacia el servidor, y la respuesta fluye en sentido contrario, desde el servidor hacia los clientes. Ejemplo: la arquitectura cliente-servidor en la web (navegadores web como clientes que solicitan páginas web a servidores web) o un sistema de base de datos (aplicaciones cliente que envían consultas a un servidor de base de datos). Analogía: una relación entre un cliente y un proveedor de servicios, donde el cliente solicita un servicio y el proveedor lo ofrece.

> [!warning] Trampa del cuestionario
> "Los clientes inician las solicitudes y el servidor escucha y responde" → comunicación **asimétrica**, también llamada **cliente-servidor**. P2P, en cambio, es **simétrica**.

## Ejercicios

1. Explica con tus propias palabras las dos formas principales de comunicación entre tareas concurrentes: memoria compartida y paso de mensajes. ¿En qué se diferencian estos dos modelos? ¿Cuáles son sus ventajas e inconvenientes relativos?
2. ¿En qué tipo de sistemas o escenarios es más habitual utilizar la comunicación por memoria compartida? ¿Y la comunicación por paso de mensajes? Justifica tus respuestas y pon ejemplos.
3. Describe cómo se puede implementar el paso de mensajes utilizando un buffer de memoria (cola de mensajes). ¿Qué tipo de sincronización es necesaria al utilizar un buffer de memoria compartido? Pon un ejemplo de un lenguaje o biblioteca que ofrezca mecanismos para el paso de mensajes basado en buffers de memoria.
4. Describe cómo se puede implementar el paso de mensajes utilizando sockets de red. ¿Para qué tipo de comunicación es especialmente adecuado el uso de sockets? ¿Qué protocolos de red suelen utilizar los sockets para la comunicación? Pon un ejemplo de un escenario donde se utilice la comunicación basada en sockets.
5. Imagina que estás diseñando un sistema concurrente para resolver un problema específico. ¿Qué factores tendrías en cuenta para decidir si utilizar comunicación por memoria compartida o por paso de mensajes en tu sistema? Considera aspectos como el rendimiento, la complejidad de la sincronización, la escalabilidad, la distribución geográfica de las tareas, etc. Pon un ejemplo de un tipo de aplicación donde sería más adecuado cada modelo de comunicación.
