## 1. Orden total vs. orden parcial

> [!definition] Orden parcial
> Conocemos el orden de ejecución **dentro de cada proceso** pero no el orden en el que se **intercala** la ejecución de los mismos.

Para entender la complejidad de la programación concurrente es fundamental comprender la diferencia en el orden de ejecución de las instrucciones entre programas secuenciales y concurrentes.

En un programa **secuencial**, el orden de ejecución está totalmente determinado y es predecible: lo establece el código y los datos que maneja. Ejecutando varias veces el mismo programa con las mismas entradas, las instrucciones siempre se ejecutan en la misma secuencia, siguiendo un camino único por el código. A este comportamiento determinista se le llama **orden total** — una línea recta donde las instrucciones van una tras otra.

En un programa **concurrente**, el orden exacto en que se intercalarán los procesos o hilos NO puede establecerse ni predecirse de antemano. Depende de factores externos al código: el planificador del SO, la carga del sistema, las interrupciones de hardware y otros eventos asíncronos. Dentro de cada hilo individual sí se mantiene el orden secuencial de sus instrucciones; el problema es la **intercalación** entre hilos. En lugar de una línea recta, son múltiples caminos que se entrelazan, y el orden preciso del entrelazado es variable e impredecible.

| | Secuencial | Concurrente |
| --- | --- | --- |
| Orden entre instrucciones propias | Total, predeterminado | Total **dentro de cada hilo** |
| Orden entre hilos | — (hay un solo flujo) | **Parcial**: impredecible |
| Depende de | Código + datos | Planificador SO, carga, interrupciones, eventos asíncronos |
| Misma entrada → misma salida | Siempre | No necesariamente |

> [!example] Ejemplo: dos hilos y un "gestor"
> Dos hilos (Hilo A y Hilo B) ejecutándose concurrentemente en un sistema multitarea. Ambos quieren la CPU; el **planificador** decide en cada momento qué hilo se ejecuta y cuánto tiempo. No sabemos de antemano si A irá primero, luego B, o cómo se intercalarán.
>
> Es como dos personas trabajando en paralelo en tareas distintas con un "gestor" que reparte el turno: cada persona sigue un orden secuencial en SU tarea, pero el orden global en que avanzan ambas es parcial e impredecible.

```java
// Cada hilo imprime sus instrucciones en orden... pero la intercalación
// de las salidas de A y B varía en cada ejecución.
public class OrdenParcial {
    public static void main(String[] args) {
        Runnable a = () -> { for (int i = 1; i <= 3; i++) System.out.println("A" + i); };
        Runnable b = () -> { for (int i = 1; i <= 3; i++) System.out.println("B" + i); };
        new Thread(a).start();
        new Thread(b).start();
    }
}
// Salida típica 1: A1 A2 B1 B2 A3 B3
// Salida típica 2: B1 B2 B3 A1 A2 A3   <- mismo código, distinto entrelazado
```

> [!note] Por qué importa
> Esta impredecibilidad del orden de ejecución es **inherente** a la programación concurrente, y es lo que introduce la complejidad y la **necesidad de sincronización** ([[1.6 - Sincronizacion]]).

## 2. Condición de carrera (race condition)

> [!definition] Condición de carrera
> Para que un programa funcione correctamente, el procesador debe ejecutar sus hilos en una determinada secuencia o *timing* de intercalación.

Un programa concurrente debe diseñarse para ser **robusto** frente a las variaciones del orden de intercalación. Que existan diferentes salidas para los mismos datos de entrada **no significa necesariamente** que el programa sea incorrecto (p. ej., un orden de impresión distinto es inofensivo). El problema aparece cuando, sin el cuidado necesario, el programa se comporta de forma **errática**: ante las mismas entradas arroja resultados erróneos en algunas ejecuciones o falla de forma inesperada.

Las condiciones de carrera son uno de los errores más comunes y difíciles de depurar en concurrencia. Pueden provocar:

| Consecuencia | Descripción |
| --- | --- |
| Resultados incorrectos o inconsistentes | Salidas erróneas o datos corruptos por falta de sincronización en el acceso a recursos compartidos. |
| Comportamiento errático e impredecible | Funciona bien unas ejecuciones y falla en otras: muy difícil de depurar y reproducir. |
| Fallos intermitentes | Pueden manifestarse solo esporádicamente o bajo ciertas condiciones de carga. |
| Vulnerabilidades de seguridad | En algunos casos un atacante puede explotarlas para comprometer el sistema. |

> [!warning] Sutiles y esporádicas
> Una race condition puede no aparecer en las pruebas porque requiere un entrelazado concreto de instrucciones que solo se da a veces ("heisenbug"). Comprender el concepto y usar sincronización adecuada es la única defensa.

## 3. Carrera de datos (data race)

> [!definition] Carrera de datos
> Condición de carrera específica para la **escritura de una variable compartida**.

Una *data race* ocurre cuando se cumplen **tres condiciones simultáneamente**:

1. Dos o más hilos acceden a la **misma variable compartida** (en memoria accesible por varios hilos).
2. **Al menos uno** de esos accesos es de **escritura**.
3. Los accesos **no están sincronizados** ni protegidos (exclusión mutua, semáforos...) para garantizar el acceso exclusivo.

En esencia: múltiples hilos leen o escriben la misma variable "al mismo tiempo", al menos uno escribe, y no hay sincronización. El valor final depende de la secuencia de ejecución y de **quién escriba el último valor** → comportamiento indefinido e resultados inesperados.

```java
// Data race clásica: dos hilos incrementan SIN protección (ver traza en 1.6)
class Contador { static int x = 0; }

public class DataRace {
    public static void main(String[] args) throws InterruptedException {
        Runnable r = () -> { for (int i = 0; i < 1_000_000; i++) Contador.x++; };
        Thread t1 = new Thread(r), t2 = new Thread(r);
        t1.start(); t2.start(); t1.join(); t2.join();
        System.out.println(Contador.x);   // ¿2000000? A veces menos: se pierden incrementos
    }
}
```

> [!tip] Siguiente paso
> *Por qué* se pierden esos incrementos a nivel de máquina (LOAD/ADD/STORE) y cómo se protege el acceso se ve en detalle en [[1.6 - Sincronizacion]] → sección crítica y exclusión mutua.

## Esquema

- **Orden total** (secuencial): instrucciones siempre en la misma secuencia, determinista.
- **Orden parcial** (concurrente): orden secuencial *dentro* de cada hilo, intercalación *entre* hilos impredecible (planificador, carga, interrupciones).
- Impredecibilidad ≠ error: solo es un problema si la **corrección** depende del orden → **condición de carrera**.
- Race conditions: resultados inconsistentes, fallos intermitentes, vulnerabilidades.
- **Data race** = caso específico: ≥2 hilos a la misma variable + ≥1 escribe + sin sincronizar.
- Causa de todo: necesidad de **sincronización** ([[1.6 - Sincronizacion]]).
