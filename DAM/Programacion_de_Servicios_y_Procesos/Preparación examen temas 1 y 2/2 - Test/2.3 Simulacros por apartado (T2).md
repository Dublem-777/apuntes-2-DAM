### Simulacro 1 · 2.1 · Ejecutar Java desde la terminal

> [!abstract] Simulacro 1
> **12 preguntas** (5 de test + 7 de hueco) · ⏱️ ~6 min · Fuente: [[Moodle 2.1 - Instalacion y configuracion de Java]] · [[2.1 - Instalación y configuracion de java|Apuntes del 2.1]] · Explicado en [[1.1 Explicacion desde cero (T1-T2)#T2.1 Ejecutar Java desde la terminal|T2.1]] · Tu nota en Moodle: **−1/12** (2 falladas, que restaron 0,5 cada una; el resto, sin contestar)

> [!question] P1 · Argumento que no es un número
> Dado el siguiente código fuente, ejecutado con el comando `java MyProgram Baldomero cincuenta`:
>
> ```java
> public class MyProgram {
> 	public static void main(String[] args) {
> 		if (args.length == 2) {
> 			try {
> 				String name = args[0];
> 				int age = Integer.parseInt(args[1]);
> 				System.out.println("Hi " + name + ", you're " + age + " years old.");
> 			} catch (NumberFormatException e) {
> 				System.out.println("Second argument must be an integer.");
> 			}
> 		} else {
> 			System.out.println("Program needs 2 arguments: a name and an age.");
> 		}
> 	}
> }
> ```
>
> ¿Cuál será la salida impresa en la consola?
> - a. Hi Baldomero, you're cincuenta years old.
> - b. Program needs 2 arguments: a name and an age.
> - c. Second argument must be an integer.
> - d. Se interrumpe la ejecución abruptamente mostrando la traza de la excepción `ArrayIndexOutOfBoundsException`.

> [!success]- Respuesta
>
> - c. ✅ Second argument must be an integer.
>
> *Por qué:* hay **2 argumentos**, así que se entra en el `if` (no sale el mensaje de "faltan argumentos"). Pero `"cincuenta"` no es un número: `Integer.parseInt` lanza **`NumberFormatException`** y se ejecuta el `catch`. No puede imprimir "cincuenta years old" porque `age` es un `int`, y no hay `ArrayIndexOutOfBoundsException` porque `args[1]` existe. [[2.1 - Instalación y configuracion de java#Argumentos de línea de comandos|Ver 2.1 · Argumentos de línea de comandos]]

> [!question] P2 · java Main.java compila en...

> [!success]- Respuesta
>
> - **memoria**
>
> *Por qué:* desde Java 11, `java Main.java` compila **en memoria**: no genera el `.class` en disco y ejecuta directamente. [[2.1 - Instalación y configuracion de java#Ejecución directa de archivos fuente|Ver 2.1 · Ejecución directa de archivos fuente]]

> [!question] P4 · Añadir al final de un fichero

> [!question] P5 · Entrada desde un fichero

>
> *Por qué:* `<` conecta un fichero a la entrada estándar: `java Programa < datos.txt` hace que `System.in` lea del fichero en vez del teclado. [[2.1 - Instalación y configuracion de java#Redirección de entrada y salida|Ver 2.1 · Redirección de entrada y salida]]

> [!question] P6 · Variable para encontrar java, javac y jar
> Para permitir la ejecución global de los comandos de desarrollo de Java (`javac`, `java`, `jar`) desde cualquier directorio en la terminal, se debe añadir la ruta del directorio binario del JDK a la variable de entorno ______.

> [!success]- Respuesta
>
> - **`PATH`**
>
> *Por qué:* **`PATH`** es la lista de carpetas donde la terminal busca los programas. Añadiendo la carpeta `bin` del JDK, `java`, `javac` y `jar` funcionan desde cualquier sitio. [[2.1 - Instalación y configuracion de java#Instalación y configuración de Java|Ver 2.1 · Instalación y configuración de Java]]

> [!question] P7 · Manifiesto sin salto de línea final
> Durante la preparación manual del archivo `META-INF/MANIFEST.MF` para crear un JAR ejecutable con la orden `jar cfm`, un desarrollador olvida incluir un salto de línea al final de la línea `Main-Class: MiClasePrincipal`. ¿Qué consecuencia tiene esto al intentar ejecutar el archivo mediante `java -jar app.jar`?
> - a. La JVM no interpretará correctamente la directiva del manifiesto y fallará al intentar localizar la clase principal.
> - b. El programa se ejecutará correctamente, pero cualquier argumento pasado por línea de comandos será ignorado silenciosamente.
> - c. La JVM añade automáticamente el salto de línea que falta durante la lectura del manifiesto en memoria.
> - d. La herramienta `jar` mostrará un error de sintaxis durante el empaquetado y abortará la creación del archivo.

> [!success]- Respuesta
>
> - a. ✅ La JVM no interpretará correctamente la directiva del manifiesto y fallará al intentar localizar la clase principal.
>
> *Por qué:* el manifiesto exige que **cada línea acabe en salto de línea**. Si falta, la JVM no reconoce `Main-Class` y no encuentra la clase principal. La herramienta `jar` no avisa al empaquetar, la JVM no lo arregla "automáticamente" y no tiene nada que ver con los argumentos. [[2.1 - Instalación y configuracion de java#Compilación, ejecución y empaquetado|Ver 2.1 · Compilación, ejecución y empaquetado]]

> [!question] P8 · Errores de cada programa en su fichero
> Se requiere ejecutar dos programas en una tubería (`java Programa1 | java Programa2`), pero se necesita que las salidas de error de ambos programas se guarden en archivos independientes (`error1.log` y `error2.log`) sin interrumpir el flujo entre ellos. ¿Cuál es la sintaxis correcta en la línea de comandos?
> - a. `java Programa1 2>&1 | java Programa2 > error1.log > error2.log`
> - b. `java -err error1.log Programa1 | java -err error2.log Programa2`
> - c. `java Programa1 2> error1.log | java Programa2 2> error2.log`
> - d. `java Programa1 | java Programa2 2> error1.log 2> error2.log`

> [!success]- Respuesta
>
> - c. ✅ `java Programa1 2> error1.log | java Programa2 2> error2.log`
>
> *Por qué:* cada `2>` va **pegado a su programa**: el de la izquierda del `|` es de Programa1 y el de la derecha, de Programa2. `2>&1` mete los errores en la tubería (lo contrario de lo pedido), Java no tiene ninguna opción `-err`, y poner dos `2>` seguidos en Programa2 solo redirige los errores de Programa2. [[2.1 - Instalación y configuracion de java#Redirección de entrada y salida|Ver 2.1 · Redirección de entrada y salida]]

> [!question] P9 · Índice del primer argumento
> En un programa Java, los argumentos pasados por línea de comandos al invocar `java MiPrograma arg1 arg2` se reciben en el método `main` como un arreglo de cadenas, donde la cadena correspondiente a `arg1` se almacena en el índice ______.

> [!success]- Respuesta
>
> - **0**
>
> *Por qué:* los arrays en Java empiezan en **0**: `arg1` está en `args[0]` y `arg2` en `args[1]`. [[2.1 - Instalación y configuracion de java#Argumentos de línea de comandos|Ver 2.1 · Argumentos de línea de comandos]]

> [!question] P10 · Errores a un fichero sobrescribiendo
> En sistemas UNIX y Windows, la redirección de la salida de error estándar a un archivo de texto reemplazando su contenido previo se realiza mediante el operador ______.

> [!success]- Respuesta
>
> - **`2>`**
>
> *Por qué:* el `2` es el número del canal de error (stderr), así que `2>` manda los errores a un fichero **sobrescribiéndolo** (`2>>` los añadiría al final). [[2.1 - Instalación y configuracion de java#Redirección de entrada y salida|Ver 2.1 · Redirección de entrada y salida]]

> [!question] P11 · Tubería y System.err ⚠️
> Se ejecuta el comando `java Programa1 | java Programa2` en una terminal de Bash. `Programa1` escribe mensajes de procesamiento regular en `System.out` y alertas de depuración en `System.err`. ¿Cómo gestiona la tubería (pipe) los flujos transmitidos por `Programa1`?
> - a. Ambos flujos `System.out` y `System.err` se combinan automáticamente y se envían a la entrada estándar de `Programa2`.
> - b. `System.err` provoca la interrupción inmediata de la tubería antes de que `Programa2` pueda procesar cualquier dato de `System.out`.
> - c. `System.err` se redirige automáticamente a un archivo temporal de registro gestionado por el sistema operativo.
> - d. `System.out` se redirige a la entrada estándar (`System.in`) de `Programa2`, mientras que `System.err` no se canaliza y se imprime directamente en la consola.

> [!success]- Respuesta
>
> - d. ✅ `System.out` se redirige a la entrada estándar (`System.in`) de `Programa2`, mientras que `System.err` no se canaliza y se imprime directamente en la consola.
>
> *Por qué:* la tubería `|` **solo conecta `System.out`** con `System.in` del siguiente. `System.err` no entra en la tubería y se ve en la **consola**. Las demás opciones inventan cosas "automáticas" (combinarlos, mandarlos a un fichero temporal) o un error que no existe (interrumpir la tubería). [[2.1 - Instalación y configuracion de java#Redirección de entrada y salida|Ver 2.1 · Redirección de entrada y salida]]
>
> ⚠️ *Fallada en el cuestionario de Moodle: repásala en el apunte.*

> [!question] P12 · Tubería llena ⚠️
> En la ejecución del pipeline `java Programa1 | java Programa2`, `Programa1` escribe datos en su salida estándar a una velocidad sustancialmente mayor de la que `Programa2` puede leerlos desde su entrada estándar. ¿Qué mecanismo aplica el sistema operativo para gestionar este desequilibrio?
> - a. `Programa2` almacena indefinidamente la salida excedente en la memoria de intercambio (SWAP) del sistema sin pausar a `Programa1`.
> - b. `Programa1` descarta silenciosamente los nuevos datos emitidos por `System.out` hasta que `Programa2` reduzca su carga de procesamiento.
> - c. `Programa1` se bloquea temporalmente cuando la tubería alcanza su capacidad máxima hasta que `Programa2` consuma datos y libere espacio.
> - d. El sistema operativo aborta el proceso de `Programa1` generando una excepción de desbordamiento de búfer (_buffer overflow_).

> [!success]- Respuesta
>
> - c. ✅ `Programa1` se bloquea temporalmente cuando la tubería alcanza su capacidad máxima hasta que `Programa2` consuma datos y libere espacio.
>
> *Por qué:* la tubería tiene un búfer limitado: cuando se llena, el que escribe (**Programa1**) **se bloquea** hasta que Programa2 lea y deje hueco. No se pierden datos, no se usa la SWAP y el SO no mata a nadie: en este tema, cuando algo va mal, alguien **se queda esperando**. [[2.1 - Instalación y configuracion de java#Redirección de entrada y salida|Ver 2.1 · Redirección de entrada y salida]]
>

> [!question] P1 · Cambiar command() después de start()
> Si se invoca el método `pbuilder.command(...)` para modificar la orden de ejecución después de haber llamado a `pbuilder.start()`, ¿qué ocurre con el subproceso recién creado?
> - a. Se envía una señal de cancelación inmediata para detener el subproceso actual antes de modificar la orden.
> - b. El subproceso ya iniciado no se ve afectado, pero la nueva configuración se aplicará a futuras llamadas a `start()`.
> - c. Se lanza inmediatamente una excepción `IllegalStateException` porque el `ProcessBuilder` queda bloqueado tras la ejecución.
> - d. El subproceso ya iniciado se reconfigura y reinicia automáticamente con la nueva lista de comandos.

> [!success]- Respuesta
>
> - b. ✅ El subproceso ya iniciado no se ve afectado, pero la nueva configuración se aplicará a futuras llamadas a `start()`.
>
> *Por qué:* `ProcessBuilder` es como un formulario: el proceso que ya salió **no se entera** de los cambios, pero los siguientes `start()` usarán la nueva orden. No se manda ninguna señal, no hay `IllegalStateException` y el proceso no se reinicia solo. [[2.2 - Gestión de subprocesos#Creación y configuración con ProcessBuilder|Ver 2.2 · Creación y configuración con ProcessBuilder]]

> [!question] P2 · getenv() vs environment()
> ¿Cuál es la diferencia fundamental entre el mapa devuelto por `System.getenv()` y el devuelto por `ProcessBuilder.environment()`?
> - a. El mapa de `System.getenv()` permite modificar variables del sistema operativo globalmente, mientras que el de `ProcessBuilder` solo afecta al proceso padre.
> - b. El mapa de `System.getenv()` es de solo lectura, mientras que el de `ProcessBuilder.environment()` es modificable y permite ajustar las variables para el subproceso.
> - c. Ambos mapas son de solo lectura, exigiendo el uso de parámetros de línea de comandos para pasar variables al subproceso.
> - d. `ProcessBuilder.environment()` devuelve un mapa vacío por defecto que debe poblarse desde cero, a diferencia de `System.getenv()`.

> [!success]- Respuesta
>
> - b. ✅ El mapa de `System.getenv()` es de solo lectura, mientras que el de `ProcessBuilder.environment()` es modificable y permite ajustar las variables para el subproceso.
>
> *Por qué:* `System.getenv()` es de **solo lectura**; `pb.environment()` es **modificable** y trae una copia de las variables del padre (no empieza vacío). Ninguno de los dos cambia las variables del SO de forma global. [[2.2 - Gestión de subprocesos#Variables de entorno y propiedades del sistema|Ver 2.2 · Variables de entorno y propiedades del sistema]]

> [!question] P4 · Directorio de trabajo por defecto
> ¿Cuál es el directorio de trabajo predeterminado (_working directory_) de un subproceso creado con `ProcessBuilder` si no se modifica expresamente mediante `directory(File)`?
> - a. La carpeta temporal del sistema definida en la variable de entorno `TEMP` o `/tmp`.
> - b. La ubicación exacta del ejecutable `java` dentro del sistema de archivos.
> - c. El directorio raíz del sistema operativo (`C:\` en Windows o `/` en Unix).
> - d. El directorio indicado por la propiedad del sistema `user.dir` del proceso padre.

> [!success]- Respuesta
>
> - d. ✅ El directorio indicado por la propiedad del sistema `user.dir` del proceso padre.
>
> *Por qué:* si no llamas a `directory(File)`, el hijo arranca en la **misma carpeta que el padre**, que es la propiedad **`user.dir`**. No es la carpeta temporal, ni la raíz, ni donde está el ejecutable `java`. [[2.2 - Gestión de subprocesos#Creación y configuración con ProcessBuilder|Ver 2.2 · Creación y configuración con ProcessBuilder]]

> [!question] P5 · Comprobaciones antes de usar Desktop

> - c. Verificar `Desktop.isDesktopSupported()` y posteriormente `desktop.isSupported(Desktop.Action)`.
> - d. Validar que el archivo exista mediante `file.exists()` y comprobar que la versión de Java sea superior a 18.

> [!success]- Respuesta
>
> - c. ✅ Verificar `Desktop.isDesktopSupported()` y posteriormente `desktop.isSupported(Desktop.Action)`.
>
> *Por qué:* primero se mira si hay escritorio con **`Desktop.isDesktopSupported()`** y luego si la acción concreta está disponible con **`desktop.isSupported(Desktop.Action.X)`**. No hay ninguna variable `DESKTOP`, ni tienen que ver la memoria, la versión de Java o los permisos de administrador. [[2.2 - Gestión de subprocesos#Abrir aplicaciones con Desktop|Ver 2.2 · Abrir aplicaciones con Desktop]]

> [!question] P8 · Error típico con cmd /c dir /o
> Al instanciar un objeto `ProcessBuilder` para ejecutar `cmd /c dir /o`, ¿cuál es un error común al pasar los comandos como argumento?
> - a. Utilizar barras diagonales `/` para los modificadores `/c` y `/o` en lugar de barras invertidas `\`.
> - b. Pasar la cadena completa `"cmd /c dir /o"` como un único argumento en el constructor.
> - c. Utilizar una lista de cadenas `List<String>` en lugar de un array varargs.

> [!question] P9 · Método de Runtime que termina la JVM

> [!question] P1 · Leer la salida del hijo
> En el modelo de comunicación por defecto entre un proceso padre y un subproceso hijo en Java, ¿qué método de la clase Process debe utilizar el proceso padre para leer la salida estándar (stdout) generada por el hijo?
> - a. `getInputStream()`
> - b. `getOutputStream()`
> - c. `getErrorStream()`
> - d. `getStandardOutput()`

> [!success]- Respuesta
>
> - a. ✅ `getInputStream()`
>
> *Por qué:* los nombres van desde el punto de vista del **padre**: lo que **entra al padre** (la salida del hijo) se lee con **`getInputStream()`**. `getOutputStream()` sirve para escribirle, `getErrorStream()` es para sus errores y `getStandardOutput()` no existe. [[2.3 - Flujos de comunicación#Flujos predeterminados entre padre e hijo|Ver 2.3 · Flujos predeterminados entre padre e hijo]]

> [!question] P2 · Cuándo se configuran las redirecciones
> ¿En qué momento debe realizarse la configuración de redirección de flujos (redirectInput, redirectOutput, etc.) mediante la API de ProcessBuilder?
> - a. Únicamente cuando el proceso hijo se encuentre en estado bloqueado.
> - b. Inmediatamente después de llamar a start(), utilizando el objeto Process obtenido.
> - c. En cualquier momento del ciclo de vida del proceso antes de llamar a waitFor().
> - d. Siempre antes de invocar el método start() del ProcessBuilder.

> [!success]- Respuesta
>
> - d. ✅ Siempre antes de invocar el método start() del ProcessBuilder.
>
> *Por qué:* las redirecciones son parámetros con los que el SO **crea** el proceso, así que van **antes de `start()`**. Después, el proceso ya está creado con sus tuberías y no sirve de nada. [[2.3 - Flujos de comunicación#Redirección de los flujos|Ver 2.3 · Redirección de los flujos]]

> [!success]- Respuesta

>
> *Por qué:* `Redirect.DISCARD` descarta el flujo: ni llega al padre ni se ve en la consola. [[2.3 - Flujos de comunicación#Redirección de los flujos|Ver 2.3 · Redirección de los flujos]]

> [!question] P4 · Deadlock por no leer la salida
> ¿Qué problema crítico de concurrencia (deadlock) puede ocurrir si un subproceso hijo produce abundante salida por stdout o stderr y el proceso padre no lee esos flujos mientras ejecuta process.waitFor()?
> - a. El flujo del subproceso hijo se redirige automáticamente al archivo out.txt para liberar espacio.
> - b. La JVM destruye automáticamente el subproceso hijo por superar el límite de memoria del búfer.
> - c. El método waitFor() lanza una IllegalThreadStateException de forma asíncrona.
> - d. La tubería del sistema operativo llena su búfer limitado, lo que provoca que el subproceso hijo se bloquee al intentar escribir, impidiendo que termine.

> [!success]- Respuesta
>
> - d. ✅ La tubería del sistema operativo llena su búfer limitado, lo que provoca que el subproceso hijo se bloquee al intentar escribir, impidiendo que termine.
>
> *Por qué:* la tubería tiene un búfer limitado: si el padre está en `waitFor()` sin leer, el búfer se llena, el **hijo se bloquea** al escribir y nunca termina. Nadie lo arregla "automáticamente" (ni un fichero, ni la JVM), e `IllegalThreadStateException` es de `exitValue()`, no de `waitFor()`. [[2.4 - Finalización de subprocesos#Drenar flujos durante la espera|Ver 2.4 · Drenar flujos durante la espera]]

> [!question] P5 · redirectErrorStream(true)
> ¿Qué efecto tiene invocar el método redirectErrorStream(true) sobre un objeto ProcessBuilder antes de iniciar el proceso?
> - a. Descarta por completo cualquier mensaje de error generado por el subproceso.
> - b. Redirige la salida estándar (stdout) directamente a la consola del padre y conserva stderr en la tubería por defecto.
> - c. Combina la salida de error estándar (stderr) con la salida estándar (stdout), haciendo que getErrorStream() devuelva un flujo nulo.
> - d. Lanza una excepción de entrada/salida si no se ha configurado previamente un archivo de destino.

> [!success]- Respuesta
>
> - c. ✅ Combina la salida de error estándar (stderr) con la salida estándar (stdout), haciendo que getErrorStream() devuelva un flujo nulo.
>
> *Por qué:* **junta** los errores con la salida normal: todo se lee por `getInputStream()` y `getErrorStream()` queda vacío. No descarta nada (eso es `DISCARD`), no manda nada a la consola (eso es `INHERIT`) y no exige ningún fichero. [[2.3 - Flujos de comunicación#Redirección de los flujos|Ver 2.3 · Redirección de los flujos]]

> [!question] P7 · Sincronización implícita
> ¿Por qué se afirma que la comunicación mediante flujos (pipes) entre un proceso padre y un subproceso produce una "sincronización implícita"?
> - a. Porque la JVM utiliza internamente cerrojos de tipo ReentrantLock para coordinar los hilos del proceso padre y el proceso hijo.
> - b. Porque la lectura y la escritura en las tuberías son operaciones bloqueantes, ajustando el ritmo de los procesos sin necesidad de mecanismos adicionales de sincronización.
> - c. Porque los procesos comparten la misma región de memoria RAM gestionada por el sistema operativo.
> - d. Porque el sistema operativo congela la ejecución del proceso hijo en cada salto de línea de su salida.

> [!success]- Respuesta
>
> - b. ✅ Porque la lectura y la escritura en las tuberías son operaciones bloqueantes, ajustando el ritmo de los procesos sin necesidad de mecanismos adicionales de sincronización.
>
> *Por qué:* leer de una tubería vacía **bloquea** al que lee, y escribir en una llena bloquea al que escribe. Así los dos procesos se acompasan solos, sin cerrojos. No comparten memoria (son procesos distintos), no hay `ReentrantLock` entre procesos y el SO no congela a nadie en cada salto de línea. [[2.3 - Flujos de comunicación#Lectura y escritura de datos|Ver 2.3 · Lectura y escritura de datos]]

> [!question] P10 · Redirect.to vs appendTo
> ¿Cuál es la diferencia fundamental entre utilizar ProcessBuilder.Redirect.to(file) y ProcessBuilder.Redirect.appendTo(file) para redirigir la salida de un proceso?
> - a. appendTo(file) permite escritura concurrente de múltiples procesos, mientras que to(file) bloquea el archivo de forma exclusiva.
> - b. to(file) sobrescribe el contenido del fichero si existe, mientras que appendTo(file) escribe al final del fichero preservando el contenido previo.
> - c. to(file) redirige únicamente la salida estándar, mientras que appendTo(file) redirige automáticamente la salida de error.
> - d. to(file) crea un archivo temporal en la carpeta del sistema, mientras que appendTo(file) requiere que el archivo ya exista.

> [!success]- Respuesta
>
> - b. ✅ to(file) sobrescribe el contenido del fichero si existe, mientras que appendTo(file) escribe al final del fichero preservando el contenido previo.
>
> *Por qué:* `to(file)` **sobrescribe** (como `>`) y `appendTo(file)` **añade al final** (como `>>`). Las dos valen para cualquier flujo de salida, ninguna exige que el fichero exista y no tienen nada que ver con escrituras concurrentes. [[2.3 - Flujos de comunicación#Redirección de los flujos|Ver 2.3 · Redirección de los flujos]]

> [!question] P33 · Métodos de control en ProcessHandle
